# SD — сервис-деск для MSP «Открытые Горизонты»

Омниканальная сервис-деск система (multi-tenant, договоры, тарифные SLA, биллинг времени) по практикам ITIL 4. Разрабатывается с нуля поэтапно, каждый этап — работающий разворачиваемый результат.

## Стек

- **Backend:** Python 3.12, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 16
- **Frontend:** React 18 + TypeScript, Vite, React Router, TanStack Query
- **Инфраструктура:** Docker Compose (app, worker, db, nginx, frontend), nginx как обратный прокси перед `app` (API, порт `HTTP_PORT`); SPA собирается Vite и отдаётся отдельным nginx-контейнером `frontend` на своём порту (`FRONTEND_PORT`) — разнесены специально, т.к. роутеры backend висят на корневых путях (`/tickets`, `/users`, ...) без префикса `/api`, что коллизирует с одноимёнными клиентскими маршрутами SPA на одном порту (см. decisions.md). Worker — отдельный процесс на том же образе backend, раз в минуту считает SLA-эскалации (`app/worker.py`); Redis появится, когда понадобится (websocket pub-sub, очереди каналов — этапы 4+)

## Запуск локально

```bash
cp .env.example .env          # при необходимости поправить значения
docker compose up -d --build
```

- Панель (SPA): http://localhost:8081 (порт — `FRONTEND_PORT`; собирается Vite и отдаётся отдельным
  nginx-контейнером `frontend` — см. «Стек» выше про то, почему не на одном порту с API)
- API: http://localhost:8080 (порт — `HTTP_PORT`, обратный прокси `nginx` → `app`)
- OpenAPI-документация: http://localhost:8080/docs
- Первый вход: `admin@o-horizons.com` / `ChangeMe123!` (задаётся `SEED_ADMIN_*` в `.env`; сменить после первого входа)

Миграции и сид выполняются автоматически при старте контейнера `app`. Если меняете `FRONTEND_API_BASE_URL`
(адрес API, который увидит браузер) — это build arg, а не runtime-переменная, контейнер `frontend` нужно
пересобрать: `docker compose up -d --build frontend`.

Для активной разработки фронтенда (hot reload) удобнее второй, независимый способ — Vite dev-сервер
поверх того же API-контейнера, без пересборки образа на каждое изменение:

```bash
cd frontend
npm install
npm run dev                   # http://localhost:5173, API берётся из VITE_API_BASE_URL (.env фронтенда)
```

## Тестирование

**Все тесты выполняются в локальном Docker** — внутри контейнера `app`, не в локальном venv:

```bash
docker compose exec app python -m pytest tests/ -q
```

pytest и бинд-маунт исходников даёт `docker-compose.override.yml` — локальный файл, который Compose подхватывает автоматически (в репозиторий не входит, в боевой образ тестовые зависимости не попадают). Если его нет, создайте:

```yaml
services:
  app:
    build: {context: ./backend, args: {INSTALL_DEV: "true"}}
    volumes: ["./backend:/srv", "./scripts:/srv/scripts:ro", "attachments:/data/attachments"]
  worker:
    build: {context: ./backend, args: {INSTALL_DEV: "true"}}
    volumes: ["./backend:/srv", "attachments:/data/attachments"]
```

Перед коммитом этапа тесты обязаны проходить полностью. Бизнес-логика SLA-расчётов и маршрутизации покрывается тестами обязательно (раздел 10 ТЗ).

## Настройка каналов (Email, MAX, Telegram и далее)

Учётные данные интеграций (IMAP/SMTP ящика поддержки, токены ботов MAX/Telegram, в будущем — Plusofon) задаются **в интерфейсе**, не в `.env`: Настройки → Каналы (`/settings/channels`, роль руководитель/администратор). Хранятся в таблице `integration_settings` — несекретные поля в открытом виде, пароли/токены зашифрованы `SETTINGS_ENCRYPTION_KEY` (см. выше) и никогда не возвращаются через API в открытом виде (только флаг «задан»). Это сделано специально, чтобы новый канал не требовал перевыпуска `.env` и передеплоя — только запись в БД через форму.

Email: приём — IMAP-опрос (интервал задаётся в настройках канала, независим от интервала SLA-эскалаций), отправка — SMTP с тегом `[#OH-<номер>]` в теме письма. Правила склейки диалога и очереди «Неизвестные» — раздел 2.3 ТЗ и [docs/decisions.md](docs/decisions.md).

Телефония (Plusofon): события звонков приходят вебхуком на `/webhooks/telephony`, защищённым общим секретом из настроек канала. Клиент опознаётся по номеру телефона контакта (та же нормализация, что и в мессенджерах), пропущенный звонок автоматически становится заявкой «Пропущенный звонок» в очереди диспетчера, карточка звонка (номер, время, длительность, запись) видна в заявке. Имена полей вебхука задаются в форме настроек — под фактический формат аккаунта, без правки кода. **Не проверено на боевом аккаунте.**

MAX и Telegram — зеркальные по функциям клиентские боты (приём/отправка через long polling, идентификация по ID контакта в канале, меню «Мои заявки»/«Создать новую»/«Закрыть заявку», «поднять старую» закрытую заявку, ответ на конкретное сообщение цитированием, уведомления клиенту о статусе/исполнителе, запрос оценки CSAT при закрытии). Общие для обоих каналов правила (статусы, цепочка клиентского закрытия, тексты бота) — в `services/messenger_common.py`, формат самого API канала — в `max_client.py`/`max_channel.py` и `telegram_client.py`/`telegram_channel.py` отдельно. **Оба проверены end-to-end на боевых токенах ботов** (входящие и исходящие сообщения, кнопки, реальный формат ответа на сообщение) — подробности и найденные вживую расхождения с публичной документацией см. в [docs/decisions.md](docs/decisions.md).
