## 1. Из чего собрано

```
          браузер                          Telegram / MAX          Zabbix, АТС
             │                                    │                     │
       ┌─────┴─────┐                              │                     │
       │ frontend  │  SPA (React + Vite),         │ long polling        │ вебхуки
       │  :8081    │  отдаётся своим nginx        │                     │
       └─────┬─────┘                              │                     │
             │ REST + WebSocket                   │                     │
       ┌─────┴─────┐                        ┌─────┴─────┐               │
       │   nginx   │────────────────────────│  worker   │               │
       │   :8080   │                        │           │               │
       └─────┬─────┘                        └─────┬─────┘               │
             │                                    │                     │
       ┌─────┴────────────────────────────────────┴─────────────────────┴──┐
       │                      app  (FastAPI, :8000)                        │
       └───────────────────────────────┬───────────────────────────────────┘
                                       │
                              ┌────────┴────────┐
                              │  PostgreSQL 16  │
                              └─────────────────┘
```

Пять контейнеров, ничего внешнего. **Ни Redis, ни очереди сообщений, ни
S3** — сознательно: система разворачивается на одной ВМ у заказчика, и
каждый дополнительный сервис это то, что кто-то должен администрировать.
Postgres умеет достаточно (`LISTEN/NOTIFY` вместо брокера), вложения лежат
на диске в томе.

| Контейнер | Роль |
|-----------|------|
| `db` | PostgreSQL 16, том `db_data` |
| `app` | REST API и WebSocket. Мигрирует БД и наполняет справочники при старте |
| `worker` | Фоновые задачи: SLA-эскалации, автоматизация статусов, плановые заявки, ежемесячные отчёты, опрос почты, long polling MAX и Telegram |
| `nginx` | Прокси перед API, включая апгрейд WebSocket |
| `frontend` | Собранный SPA на своём nginx. Панель сотрудника и кабинет клиента — один бандл, ветвится по пути `/portal` |

Зависимостей мало и они обычные: FastAPI, SQLAlchemy 2, Alembic, Pydantic v2,
httpx, openpyxl (XLSX), reportlab (PDF).

## 2. Слои backend

```
api/routers/    HTTP: разбор запроса, коды ответов, проверка прав
     ↓
services/       Бизнес-логика. Здесь живут все правила
     ↓
models/         SQLAlchemy-модели
```

Правило одно: **логика не живёт в роутерах**. Роутер разбирает запрос,
проверяет права и зовёт сервис. Это не эстетика — почти каждая операция
вызывается из трёх мест: из API, из бота и из воркера. Заявка, созданная
ботом, обязана пройти через ту же маршрутизацию, SLA и биллинг, что и
заведённая диспетчером, поэтому все они зовут `tickets_service.create_ticket`.

### Точки, о которых надо знать

| Что | Где | Почему важно |
|-----|-----|--------------|
| Видимость заявок сотруднику | `services/ticket_access.py` | Единственное место, где решается «что моё». Проверка стоит в `_get_ticket_or_404`, через который проходят все эндпоинты заявки |
| Видимость заявок клиенту | `services/portal.py` → `visible_tickets_query` | То же для портала |
| Общие правила ботов | `services/messenger_common.py` | MAX и Telegram зеркальны; всё, кроме формата API канала, живёт здесь, чтобы каналы не разъехались |
| Доставка уведомлений | `services/staff_notifications.py` | Колокольчик, живой push и Telegram — один канал для всех событий |
| Аудит настроек | `services/settings_audit.py` | Слушатель `before_flush`, пишет изменения сам. Новый роутер настроек не нужно ничему учить |
| SLA | `services/sla.py` + `calendar_math.py` | Сроки считаются рабочими минутами по календарю тарифа |

## 3. Как приходит обращение

```
Telegram/MAX (long polling)  ─┐
Email (IMAP-опрос)           ─┤
Портал (REST)                ─┼──→ resolve_contact ──→ create_ticket ──→ очередь
Телефония (вебхук)           ─┤         │                    │
Мониторинг (вебхук)          ─┘         │                    ├─ приоритет (матрица или вручную)
                                        │                    ├─ договор и тариф → SLA-сроки
                            не опознан ─┘                    ├─ маршрутизация → инженер/группа
                                        │                    └─ уведомление адресату
                                        ↓
                              организация «Неизвестные»
```

Обращение **никогда не теряется**. Не удалось опознать клиента — заявка всё
равно создаётся, в организацию «Неизвестные», и диспетчер разбирается.
Аналогично алерт мониторинга с неизвестной организацией.

## 4. Решения, которые выглядят странно, пока не знаешь причины

**Postgres `LISTEN/NOTIFY` вместо брокера.** Уведомления рождаются в
`worker`, а websocket держит `app` — нужен канал между процессами.
`pg_notify` выполняется внутри транзакции, поэтому клиента не будят ради
строки, которую откатит rollback. Опрос раз в 30 секунд оставлен запасным
путём: websocket рвётся о прокси и спящий ноутбук.

**Секреты интеграций в БД, а не в `.env`.** Токены ботов и пароли почты
задаются в интерфейсе и шифруются Fernet-ключом из
`SETTINGS_ENCRYPTION_KEY`. Новый канал не требует перевыпуска `.env` и
передеплоя. Обратная сторона: **смена ключа делает старые секреты
нечитаемыми** — см. deployment.md.

**Отчёт клиенту хранится снимком.** Документ, уходящий наружу, не должен
меняться от списания, внесённого задним числом. Свежие цифры — только по
явной команде «сформировать заново».

**`Enum(native_enum=False)` хранит имена, а не значения.** В БД лежит
`INCIDENT`, а не `incident`. Это ловушка для сырого SQL: вставка значений
даст строки, которые ORM откажется читать.

**Инженеру видны нераспределённые заявки.** ТЗ говорит «свои и групповые»,
но там же требуется самоназначение — взять в работу невидимое нельзя.

## 5. Схема данных, кратко

Ядро: `organizations` → `contacts` → `tickets` → `messages` / `time_entries`.

- `contracts` связывает организацию с `tariffs`, тариф несёт `tariff_sla_rules`
  (сроки по приоритетам) и `business_calendars` (рабочие часы, праздники).
- `tickets.parent_ticket_id` — связь «поднятой» заявки с прежней.
- `audit_logs` — журнал по заявкам и настройкам.
- `client_reports` — снимки отчётов, JSONB.
- `integration_settings` — настройки каналов, секреты шифруются.

**Каждая модель должна быть в `app/models/__init__.py`.** Alembic берёт
метаданные оттуда: незарегистрированная модель для автогенерации не
существует, и `--autogenerate` предложит удалить её таблицу. Полнота
проверяется тестом `test_all_models_are_registered`.

## 6. Тесты

404 теста, `pytest`, гоняются **внутри контейнера**:

```bash
docker compose exec app python -m pytest tests/ -q
```

Каждый тест идёт в savepoint поверх уже наполненной dev-базы и откатывается.
Отсюда важное следствие: **нельзя писать проверки на глобальные счётчики**
(«всего сработало 1») — в базе живут настоящие данные от ручных проверок.
Проверяйте объект, который создал сам тест. На этом обжигались трижды.

Отдельно стоит `test_model_registry.py` — он ловит дрейф схемы относительно
моделей и незарегистрированные модели.

## 7. Что проверяется только руками

Тесты покрывают бизнес-логику, но систематически **не видят стыков**. Все
находки последних этапов были именно там: разбор HTTP-заголовка,
сериализация ответа, двойное уведомление при создании заявки, звук на старом
хвосте уведомлений при загрузке страницы.

Поэтому перед сдачей изменений:

- **боты** — прогнать живой диалог с реальным токеном;
- **интерфейс** — открыть в браузере, а не поверить типам;
- **вебхуки** — отправить настоящее событие, а не только вызвать сервис.

Скрипты браузерных проверок писались одноразовыми под каждую задачу
(Playwright) — постоянного набора e2e нет; это осознанный остаток.
