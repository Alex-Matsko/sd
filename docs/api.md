# API

Интерактивная документация со всеми полями — на самом сервере:
`http://<сервер>:8080/docs` (Swagger, генерируется из кода и всегда
актуальна). Здесь — то, чего в ней нет: как аутентифицироваться, как
устроены права и пагинация, и где брать данные для биллинга.

---

## 1. Аутентификация

Два независимых контура. Токен одного **не работает** в другом: у клиента и
сотрудника разные популяции и разные права.

### Сотрудник

```bash
curl -X POST https://api.sd.example.com/auth/login \
     -d 'username=user@o-horizons.com&password=...'
# {"access_token": "...", "refresh_token": "..."}
```

Форма, а не JSON — стандартный `OAuth2PasswordRequestForm`. Дальше во всех
запросах:

```
Authorization: Bearer <access_token>
```

Access-токен живёт 30 минут, refresh — 30 дней. Обновление:

```bash
curl -X POST https://api.sd.example.com/auth/refresh \
     -H 'Content-Type: application/json' \
     -d '{"refresh_token": "..."}'
```

Каждое обновление **отзывает старый refresh** и выдаёт новый. Смена или
сброс пароля гасит все refresh-токены пользователя.

> Десять неудачных попыток входа закрывают его на 15 минут — ответ `429` с
> заголовком `Retry-After`. Счёт идёт и по адресу, и по IP. Учитывайте это
> в интеграциях: не повторяйте вход в цикле.

### Клиент портала

`POST /portal/auth/login` возвращает токен с `type: "portal"`. Он даёт
доступ только к `/portal/*` и только к данным своего контакта (или своей
организации, если у контакта стоит соответствующий флаг).

### Вебхуки

Телефония и мониторинг приходят без токена — у АТС и Zabbix нет сессии.
Защита общим секретом в заголовке `X-Webhook-Secret` (или `?secret=`).
Секрет задаётся в интерфейсе и должен состоять из латиницы, цифр и знаков
препинания: он едет HTTP-заголовком.

## 2. Права

Роль сотрудника определяет доступ; отказ приходит как `403`, а недоступная
заявка — как **`404`, а не `403`**: иначе по кодам ответа перебираются
существующие номера.

| Роль | Заявки |
|------|--------|
| `engineer` | свои, своей группы и нераспределённые |
| `dispatcher` и выше | все |

Настройки (тарифы, SLA, маршрутизация, пользователи, интеграции) —
`manager` и `admin`. Справочники и контакты — `dispatcher` и выше.

Общие отчёты (`/reports/*`) и сохранённые клиентские отчёты (`/client-reports*`),
включая скачивание PDF/XLSX, доступны только `manager` и `admin`.

Любое изменение настроек попадает в `audit_logs` с автором.

## 3. Пагинация

Списки, которые могут вырасти, принимают `limit` и `offset`, а полное число
совпадений отдают **заголовком**, не в теле:

```bash
curl -D- 'https://api.sd.example.com/tickets?limit=50&offset=0' -H "Authorization: Bearer $T"
# X-Total-Count: 1043
# [ { ... }, ... ]
```

Тело остаётся обычным массивом — так не ломаются потребители, написанные до
появления пагинации. Максимум на страницу — 200.
Заголовок `X-Total-Count` открыт для чтения браузером через CORS.

Дополнительные фильтры `GET /tickets`: `open_only=true` — открытые статусы;
`exclude_archived=true` — все, кроме закрытых и отменённых (область канбана);
`overdue=true` — открытые заявки с просроченным, неприостановленным сроком решения.
Фильтры применяются до подсчёта и пагинации.

`GET /tickets/stats?tz=Europe/Istanbul` считает «сегодня» и дни недельного
графика в указанном часовом поясе IANA; по умолчанию используется UTC.

## 4. Данные для биллинга

ТЗ р. 5 требует, чтобы биллинговые данные были доступны через API для
будущей интеграции с 1С:УНФ (сама интеграция — вне объёма v1).

**Расход пакета часов организации за месяц:**

```bash
curl 'https://api.sd.example.com/organizations/1/usage?year=2026&month=8' \
     -H "Authorization: Bearer $T"
```

```json
{
  "organization_id": 1,
  "year": 2026,
  "month": 8,
  "package_total_minutes": 600,
  "package_used_minutes": 0,
  "package_remaining_minutes": 600,
  "overage_minutes": 0,
  "overage_cost": 0.0
}
```

Без параметров — текущий месяц.

**Списания по заявке:** `GET /tickets/{id}/time-entries`. У каждой записи
есть `billed_package_minutes` и `billed_overage_minutes` — раскладка,
зафиксированная на момент списания. Сумма этих двух полей всегда равна
`duration_minutes`.

**Готовый отчёт клиенту за период** (снимок, тот же документ, что уходит
клиенту):

```
GET  /client-reports?organization_id=1     список сформированных
POST /client-reports                       сформировать за период
GET  /client-reports/{id}                  содержимое снимка
GET  /client-reports/{id}/pdf              PDF
GET  /client-reports/{id}/xlsx             XLSX
```

Цифры в снимке зафиксированы: списание, внесённое задним числом, попадёт в
отчёт только после повторного формирования. Для интеграции это то, что
нужно — выгруженная в 1С сумма не поедет задним числом.

**Сводная аналитика:** `GET /reports/overview?date_from=&date_to=&organization_id=`.

## 5. Живые уведомления

WebSocket: `wss://api.sd.example.com/ws/notifications?token=<access_token>`

Токен передаётся параметром адреса — браузерный WebSocket не умеет ставить
заголовки. Соединение с портальным или неверным токеном **принимается и
сразу закрывается кодом 1008**: закрытие до `accept()` даёт клиенту
бессмысленный `1006`, по которому не отличить отказ в доступе от оборванной
сети.

Сообщение:

```json
{"user_id": 12, "type": "ticket_assigned", "title": "…", "ticket_id": 1042}
```

Типы: `ticket_assigned`, `ticket_unassigned`, `customer_replied`,
`sla_reaction_warning`, `sla_reaction_breach`, `sla_resolution_warning`,
`sla_resolution_breach`.

Не полагайтесь на websocket как на единственный путь: он рвётся о прокси и
спящий ноутбук. В панели он дополнен опросом `GET /notifications` раз в 30
секунд, и то же стоит делать интеграции.

## 6. Приём событий извне

```
POST /webhooks/telephony    события звонков (Plusofon)
POST /webhooks/monitoring   алерты мониторинга (Zabbix)
```

Оба отвечают `202` даже на неразобранное тело — отправитель с повторами
иначе долбил бы эндпоинт вечно; причина пишется в лог и в тело ответа.
Идемпотентны по идентификатору события источника: повторная доставка не
плодит заявки.

Имена полей настраиваются в интерфейсе без правки кода — см.
[monitoring.md](monitoring.md).

## 7. Ошибки

Обычные коды HTTP, текст — в поле `detail`, по-русски (он показывается
пользователю):

```json
{"detail": "Секрет вебхука должен состоять из латинских букв, цифр и знаков препинания…"}
```

| Код | Когда |
|-----|-------|
| `400` | Неверные данные запроса |
| `401` | Нет токена, истёк или не того типа |
| `403` | Роли не хватает |
| `404` | Нет объекта — либо он есть, но недоступен вам |
| `409` | Конфликт: дубль email, повторная оценка заявки |
| `429` | Слишком много попыток входа |
| `503` | Интеграция не настроена; нет шрифта для PDF |


## Надёжная переписка и состояние системы

`POST /tickets/{id}/messages/send` принимает multipart: `payload` — JSON полей MessageCreate,
`files` — до десяти файлов, суммарно до 48 МБ. Передавайте UUID `request_id` для безопасного повтора
после потери HTTP-ответа. Повтор того же запроса возвращает сохранённое сообщение;
тот же UUID с другим содержимым — 409. Старый JSON-маршрут создания сообщения сохранён.

`MessageRead.delivery` содержит состояние, число попыток, следующую попытку, безопасное описание
ошибки и время подтверждения каналом. `POST /tickets/{id}/messages/{message_id}/delivery/retry`
повторяет ошибочную отправку с проверкой видимости заявки.

Для руководителя и администратора: `GET /operations/status`, `GET /operations/jobs`,
`GET /operations/jobs/{id}/source`, `POST /operations/jobs/{id}/retry`,
`POST /operations/jobs/{id}/discard` (JSON с полем `reason`, от 5 до 500 символов).
Журнал не возвращает токены каналов; исходные входящие события доступны только через защищённый маршрут.

Для портала добавлен `POST /portal/tickets/{id}/messages/send`: multipart с `body`, UUID `request_id`
и `files`. Автор и доступ к заявке проверяются по клиентской сессии.

Гарантии, повторные попытки и проверки готовности: [channel-reliability.md](channel-reliability.md).
