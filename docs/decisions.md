# Решения и уточнения к ТЗ

Дополняет [`TZ.md`](./TZ.md). Каждая запись — решение, принятое по ходу разработки там, где исходное ТЗ оставляло свободу трактовки. Новые решения дописывать в конец, не переписывать историю.

## Зафиксировано с заказчиком (2026-07-20)

### Номер заявки (Ticket ID)
Формат: `OH-<порядковый номер>`, например `OH-1042`. Сквозная нумерация по всей системе, без сброса по годам. Используется как тег `[#OH-1042]` в теме письма, в кнопках Telegram/MAX, в портале и в API.

### SLA/договор при отсутствии активного договора у организации
При создании заявки, если у организации нет активного договора: применяется тариф по умолчанию (базовый SLA), заявка создаётся и обрабатывается сразу. В карточке — пометка «нет активного договора» для диспетчера/руководителя, организационный вопрос решается параллельно, не блокируя работу по заявке.

### Биллинг на границе пакета часов
Если списание времени пересекает остаток пакета (например, остался 1 час, списано 3), запись делится пропорционально: часть — в счёт пакета, часть — по ставке сверх лимита. На уровне модели `TimeEntry` одна пользовательская запись времени может породить два расчётных отрезка (пакетный/сверхлимитный) для биллинга и отчётности, при этом пользователь видит и редактирует её как одну запись.

### SLA при переоткрытии заявки клиентом
Клиент отвечает на «Решённую» заявку в течение окна автозакрытия → заявка возвращается «В работе», исполнитель уведомлён. SLA по решению **не пересчитывается**: исходный результат (выполнено/нарушено) фиксируется как окончательный на момент первого перевода в «Решена». Работа после переоткрытия не создаёт новый дедлайн решения. Факт переоткрытия фиксируется в истории заявки (audit log) как есть, отдельная метрика reopen-rate — не в объёме v1, но поле для неё не блокируется на будущее.

## Предположения по умолчанию (озвучены, возражений не поступило — считаются принятыми)

- **Матрица Impact × Urgency**: стандартная ITIL-подобная таблица 3×3 → P1–P4, задаётся сид-данными, редактируется в настройках.
- **Порядок правил маршрутизации**: правило «организация → выделенный инженер» (более специфичное) применяется раньше правила «категория → группа»; при отсутствии совпадений — общая очередь диспетчера. Порядок — настраиваемое поле, не хардкод.
- **Бизнес-календари**: универсальная структура (окна по дням недели + справочник праздников РФ, редактируемый по годам). Сид-данные: 2–3 примера календаря (обычный офисный, продлённый, 24×7) с рабочими часами-заглушками — реальные часы для тарифов заказчик задаёт через настройки.
- **Сущность «Группа/команда» (Team)**: не описана явно в разделе 3 ТЗ, но нужна для маршрутизации по категории и для эскалации «руководителю группы». Вводится как отдельная сущность с полем «руководитель группы».
- **VIP-признак контакта**: в v1 — только визуальная метка для диспетчера/инженера, без автоматического влияния на приоритет или SLA. Поведение можно добавить позже без изменения схемы (поле уже булево).
- **Непривязанный контакт при автопривязке письма по домену организации**: заявка создаётся и обрабатывается сразу; контакт помечается «не подтверждён» до подтверждения диспетчером — не блокирует обработку заявки.
- **Мессенджер: клиент не ответил на запрос бота «к какой заявке относится сообщение»**, а написал следующее сообщение: ведём себя как в email-правиле — прикрепляем к последней активной заявке с пометкой для диспетчера.
- **Лимит размера вложения по умолчанию**: 25 МБ, настраиваемый параметр.

## Открытые вопросы (не блокируют Этап 1, решить до соответствующего этапа)

- Точные рабочие часы бизнес-календарей по факту (нужны реальные значения по тарифам заказчика) — до Этапа 3.
- Домен/поддомен и способ выпуска TLS-сертификата для портала клиента — до Этапа 8.
- Учётные данные интеграций: Telegram bot token, MAX bridge, Plusofon API-ключи, IMAP/SMTP почтового ящика поддержки — по мере входа в соответствующие этапы (4–6).

## Технические примечания по реализации Этапа 3 — SLA-движок (2026-07-22)

### Модель хранения дедлайнов
Срок решения хранится как абсолютный `sla_resolution_due_at`, а не как «оставшийся бюджет» — при постановке на паузу и снятии с паузы пересчитывается как `created_at + рабочее_время(бюджет_SLA + накопленная_пауза_в_рабочих_минутах)`. Пауза считается в рабочих минутах календаря (не в календарных), чтобы пауза на выходные не съедала рабочий бюджет. Один и тот же механизм пересчёта используется и при снятии с паузы, и при смене приоритета вручную.

### Фиксация результата (met/breached)
`sla_reaction_met` и `sla_resolution_met` — тройное состояние (`NULL` = ещё не решено, `true`/`false` = зафиксировано). Фиксируются один раз: по реакции — первым исходящим сообщением инженера или сработавшей эскалацией 100%; по решению — первым переводом в «Решена» или эскалацией 100%. После фиксации значение не пересчитывается (согласуется с более ранним решением про SLA при переоткрытии). Смена приоритета обнуляет `met=false`, если новый дедлайн ещё не наступил (иначе нарушение, уже случившееся по старому таймеру, осталось бы «зависшим» несправедливо), но никогда не трогает уже свершившийся положительный результат.

### Эскалации 75%/100%
Отдельный процесс-воркер (`app/worker.py`, контейнер `worker` в compose) раз в `WORKER_INTERVAL_SECONDS` (по умолчанию 60 с) сканирует открытые заявки без зафиксированного результата. На 75% бюджета — уведомление исполнителю (или руководителю группы, если не назначен); на 100% — фиксация нарушения и уведомление исполнителю **и** руководителю группы одновременно. Разовые метки `sla_*_warned_at`/`sla_*_escalated_at` на заявке гарантируют, что каждое уведомление уходит ровно один раз; сбрасываются при пересчёте по смене приоритета.

### Уведомления — только in-app на этом этапе
Добавлена таблица `notifications` и раздел в topbar (колокольчик, список, «прочитать все»). Доставка в личный Telegram инженера — по ТЗ раздел 8, реализуется в Этапе 4 вместе с остальной телеграм-интеграцией; модель уведомлений уже не потребует миграции под это.

### Обратная совместимость: заявки, созданные до Этапа 3
Колонки SLA существовали как nullable ещё с Этапа 1 (расчёт на будущее движка), поэтому заявки, созданные в Этапах 1–2, имеют `sla_reaction_due_at`/`sla_resolution_due_at = NULL`. При каждом старте `app.seed` теперь докатывает дедлайны для таких заявок — но **только если заявка ещё не продвинулась** (нет ни первого ответа, ни решения): для уже отвеченных/решённых до появления движка результат не переоценивается задним числом (не «придумываем» нарушение/выполнение по правилу, которое в момент события не действовало). Такие заявки остаются в состоянии «без SLA» — по замыслу, это не баг, а сознательная граница ответственности движка.

### Гонка контейнеров при старте
`worker` и `nginx` теперь зависят от `app` через Docker healthcheck (`condition: service_healthy`), а не просто от готовности `db` — иначе воркер иногда успевал обратиться к БД до применения миграций `app`-контейнером (замечено в разработке: первый цикл воркера падал на `UndefinedColumn`, второй проходил штатно благодаря ретраю, но само по себе полагаться на ретрай — не решение).

## Технические примечания по реализации Этапа 4 — Email-канал (2026-07-22)

### Универсальные настройки каналов вместо `.env`
По запросу заказчика учётные данные интеграций (IMAP/SMTP сейчас; Telegram bot token, MAX bridge, Plusofon API-ключи на будущих этапах) вынесены из `.env` в БД и редактируются в интерфейсе (Настройки → Каналы, раздел 8 ТЗ). Реализовано одной универсальной таблицей `integration_settings` (канал → JSON `config` + JSON `secrets_encrypted`), а не отдельной типизированной моделью на каждый канал — новый канал не требует новой миграции, только согласование ключей конфига на уровне приложения. Секреты шифруются `Fernet` (ключ `SETTINGS_ENCRYPTION_KEY` в `.env` — это единственное, что осталось «инфраструктурным» и не переехало в БД, т.к. без него сами секреты не расшифровать) и никогда не отдаются через API в открытом виде — только флаг, какие ключи заданы. Frontend показывает пароль/токен как пустое поле «оставьте пустым, чтобы не менять» плюс кнопку «Очистить», а не сам секрет.

### Приоритет привязки входящего письма к заявке
Реализовано строго по разделу 2.3: (1) заголовки In-Reply-To/References против `Message.email_message_id`, сохранённого на предыдущих исходящих письмах этой же заявки; (2) тег `[#OH-<номер>]` в теме; (3) единственная открытая заявка контакта; (4) несколько открытых заявок без совпадения по заголовкам/тегу → последняя активная (по `updated_at`, с `id` как детерминированным тай-брейкером — `now()` в Postgres одинаков для всех операторов одной транзакции, поэтому только timestamp недостаточен) с автоматической внутренней заметкой-пометкой для диспетчера; (5) открытых заявок нет → новая заявка. Новая заявка от письма создаётся с типом Incident и приоритетом P3 (ручной, с причиной «автоматически создано по email») — реальные Impact/Urgency клиент по почте не указывает, дальнейшую классификацию делает диспетчер/инженер.

### Очередь «Неизвестные»
Письма с адреса, не совпадающего ни с одним контактом и не относящегося к зарегистрированному корпоративному домену организации (включая все публичные домены из `PublicEmailDomain`), попадают в заявки организации-заглушки «Неизвестные» (создаётся лениво при первом обращении, ищется по имени — тот же приём, что и зарезервированный `code` тарифа по умолчанию). Контакт создаётся с `is_confirmed=false`. Полноценный UI «перепривязать контакт и его заявки к другой организации» не реализован в этом этапе — диспетчер видит такие заявки через фильтр по организации «Неизвестные» в общей очереди; отдельный экран разбора — кандидат на один из следующих этапов, если появится такая необходимость.

### Обработка ошибок при IMAP-опросе
Письмо считается обработанным, как только оно прочитано через `FETCH RFC822` (IMAP помечает `\Seen` автоматически) — даже если разбор/создание заявки после этого упало с исключением. Альтернатива («не помечать как прочитанное при ошибке») ведёт к бесконечному повтору одного и того же письма при системной ошибке разбора и риску дублирования уже частично созданных сущностей. Каждая ошибка полностью логируется для последующего ручного разбора; это компромисс, осознанно принятый для v1.

### Что не реализовано в этом проходе Этапа 4
ТЗ относит к Этапу 4 также «уведомления инженерам в Telegram» — это осталось не сделанным (нет Telegram-бота, нет доставки уведомлений о новых заявках/эскалациях в личный чат инженера). Инфраструктура настроек уже готова к этому: в `integration_settings` заведена заглушка канала `telegram` (переключатель «включён», без полей конфигурации), форма появится вместе с реализацией самого бота.

## Технические примечания по реализации Этапа 5 — канал MAX (2026-07-22)

### Референсной реализации не было — разработка с нуля
Ранее упомянутый в ТЗ рабочий MAX-бридж заказчика (long polling + SQLite mapping) в итоге так и не был доведён до конца и не был предоставлен как референс. Канал реализован с нуля по официальной документации `dev.max.ru/docs-api`, полученной через веб-поиск на момент разработки (2026-07-22) — **без доступа к боевому токену бота для проверки реальных ответов сервера**. Зафиксированные из документации факты:

- Домен API: `platform-api2.max.ru` (старый `platform-api.max.ru` выводится из эксплуатации к 2026-07-19 — уже пройдено на момент разработки, поэтому используется только новый).
- Авторизация: заголовок `Authorization: <токен>` без префикса `Bearer`.
- Приём: `GET /updates` (long polling, поля `marker`/`timeout`/`limit`), продакшен официально рекомендует webhook, но клиент прямо просил long polling (как и было в его прежнем бридже) — самостоятельный TLS-эндпоинт с публичным сертификатом не нужен, что соответствует общему принципу ТЗ «self-hosted без белого IP».
- Отправка: `POST /messages` (`chat_id`, `text`, вложения через `attachments`, кнопки — через `inline_keyboard`).
- Структура события: `update_type` (`message_created`/`message_callback`/`bot_started`/…), сообщение — `sender.user_id`, `recipient.chat_id`, `body.text`.

Разбор входящих событий (`_extract_incoming` в `app/services/max_channel.py`) сознательно защитный — все обращения к полям через `.get()` с проверкой на `None`, а не через прямой доступ по ключу: если реальный сервер вернёт другую форму данных, обработчик залогирует и пропустит событие вместо падения. **Перед вводом в эксплуатацию обязательно нужно завести тестового бота и сверить реальные структуры событий с кодом** — вся точка входа для правок сосредоточена в этой одной функции.

### Маркер long polling хранится в БД, не в памяти процесса
`marker` (курсор `/updates`) сохраняется в `integration_settings.config._marker` после каждого опроса — иначе перезапуск воркера заново получал бы уже обработанные события. Побочный эффект: если администратор пересохранит настройки канала MAX через интерфейс, маркер будет затёрт (форма отправляет весь `config` целиком) и бот один раз перечитает недавние события повторно. Это осознанно принятый компромисс (редкое действие администратора, ограниченный и не разрушительный повтор) в обмен на простоту — не заводили отдельное хранилище только ради этого поля.

### MAX-опрос — в отдельном потоке воркера, не в общем тике
`GET /updates` блокируется на сервере до `timeout` секунд (до 90). Если бы этот вызов стоял в общем цикле воркера рядом с SLA-эскалациями и опросом почты (`app/worker.py`), долгий опрос MAX откладывал бы SLA-эскалации на то же время. Поэтому MAX-поллинг вынесен в отдельный `threading.Thread`, независимый от основного тика; общий цикл (SLA раз в минуту + email по своему интервалу) не блокируется.

### Правила склейки диалога и очередь «Неизвестные» — идентичны email
Одна открытая заявка — сообщение в неё; несколько — бот показывает кнопки списком (плюс «Создать новую»), при ответе обычным текстом вместо кнопки — привязка к последней активной с внутренней пометкой для диспетчера (тот же принцип, что и в письмах, см. примечания Этапа 4). Активная заявка контакта хранится в новой таблице `channel_conversation_states` (одна запись на пару канал+внешний ID пользователя) и держится, пока клиент не переключится через «Мои заявки» или заявка не перестанет быть открытой. Явное создание новой заявки — командой/кнопкой «Создать новую» — переводит диалог в режим ожидания следующего сообщения как описания проблемы. Неопознанные отправители (MAX ID не привязан ни к одному контакту) уходят в ту же организацию-заглушку «Неизвестные», что и email (`app/services/unknown_queue.py`, вынесен в общий модуль вместо дублирования).

### CSAT: добавлено раньше срока (Этап 9 по плану), т.к. это часть функций бота
Раздел 2.1/2.2 ТЗ прямо перечисляет «оценка после закрытия (1–5)» как функцию бота — поэтому запрос оценки (кнопки 1–5) и приём ответа реализованы уже сейчас: при переводе заявки в «Закрыта» (`services/tickets.transition_status`) для заявок канала MAX отправляется запрос, ответ по кнопке фиксируется в `Ticket.csat_rating`/`csat_rated_at` (первая оценка финальна, повторные попытки игнорируются). Полноценная отчётность CSAT (сводные показатели, разрез по инженерам/организациям) остаётся в Этапе 9 — колонки уже есть, повторной миграции не потребуется.

### Вложения от клиента через MAX — только при наличии прямой ссылки
MAX отдаёт вложения как типизированные payload'ы; официально описанный способ получения файла по токену через отдельный запрос не проверялся вживую. Вложение сохраняется, только если в его payload сразу есть `url` для скачивания (по документации это в целом относится к изображениям) — иначе событие логируется и пропускается с пометкой «требует проверки на боевом токене», без попытки угадать неподтверждённый API вызова. Исходящие вложения (файл от инженера клиенту в MAX) в этом проходе не реализованы вовсе.

## Проверка канала MAX на боевом токене (2026-07-31)

Заказчик предоставил реальный токен своего бота. Проверка вживую вскрыла и позволила закрыть три расхождения с тем, что было написано по одной только публичной документации (см. примечания по Этапу 5 выше) — обновляю здесь итоговое состояние.

### Сертификат MAX подписан российским государственным УЦ — обычные образы Linux ему не доверяют
`platform-api2.max.ru` отдаёт цепочку, подписанную `Russian Trusted Sub CA` → `Russian Trusted Root CA` (Минцифры России) — это не входит в стандартный набор доверенных корневых сертификатов Mozilla/Debian, на котором собран `python:3.12-slim`. Без этого сертификата ЛЮБОЕ обращение к MAX API падает с `SSL: CERTIFICATE_VERIFY_FAILED`, независимо от корректности токена или кода. Это не ограничение среды разработки — то же самое будет на любой не-российской по умолчанию системе, включая продовую ВМ заказчика, если на ней не установлен этот корневой сертификат отдельно от общей системы.

Решение: корневой сертификат (`backend/certs/russian-trusted-root-ca.pem`, официально выпущен Минцифры 2022 г., до 2032 г.) закоммичен в репозиторий и устанавливается в образ на этапе сборки (`Dockerfile`: `COPY` + `update-ca-certificates`) — воспроизводимо, без обращения к внешним источникам при каждой сборке. Сертификат получен и проверен через публичный GitHub-репозиторий (независимое зеркало официального сертификата), затем подтверждён вручную через `openssl s_client` — сервер сам присылает промежуточный Sub CA в хендшейке, поэтому в доверенных достаточно только корневого.

### `httpx` не использует системное хранилище сертификатов ОС по умолчанию
Даже после установки российского сертификата в систему запросы `httpx` (используется в `max_client.py`) продолжали падать с той же ошибкой — потому что `httpx` при `verify=True` (значение по умолчанию) проверяет сертификат по **своему собственному** пакету `certifi` (курируемый список Mozilla), а не по системному `/etc/ssl/certs/ca-certificates.crt`, который обновляет `update-ca-certificates`. Это общая особенность `httpx`/`requests`, а не что-то специфичное для этого проекта — но именно из-за неё установка сертификата в ОС сама по себе ничего не чинит для Python-кода на `httpx`. Решение: `max_client.py` явно передаёт `verify="/etc/ssl/certs/ca-certificates.crt"` в оба `httpx.Client(...)` (с проверкой `os.path.exists` и откатом на стандартное поведение `httpx`, если файла нет — например, при локальном запуске вне Docker).

### `chat_id` в `POST /messages` — параметр запроса, а не поле JSON-тела
Публичная документация (и, соответственно, первоначальная реализация) предполагала `{"text": ..., "chat_id": ...}` в теле запроса. На боевом токене это стабильно возвращало `400 {"code":"proto.payload","message":"Unknown recipient"}` — ответ, который выглядит как «неизвестный получатель», но на деле означает «получатель не там, где я его ищу»: реальный API ожидает `chat_id` как query-параметр (`POST /messages?chat_id=...`), а тело запроса содержит только содержимое сообщения (`text`, `attachments`). Исправлено в `max_client.send_message`; поведение зафиксировано регресс-тестами на `httpx.MockTransport` (`tests/test_max_client.py`), чтобы это не могли случайно отменить в будущем.

**Итог:** после этих трёх правок полный цикл проверен вживую от начала до конца — входящее сообщение в реальном боте создало настоящую заявку (OH-917) с корректным разбором отправителя, а исходящий ответ инженера дошёл до реального MAX-аккаунта (подтверждено эхом от API с именем бота отправителя). Формат `Update`/`Message`, который был описан как «неподтверждённый» в примечаниях по Этапу 5, теперь подтверждён 1:1 с реальным API для `message_created` — по прежнему не проверены только вложения и `message_callback`/`bot_started`, они не встречались в реальном трафике при этой проверке.

## Внеплановые доработки по запросу заказчика (2026-07-31)

Заказчик посмотрел визуальный мокап интерфейса (сгенерированный как референс на основе уже собранного дизайна) и запросил доработки текущего рабочего интерфейса вне очереди этапов ТЗ: канбан-доска очереди, движок автоматизации статусов, углублённая карточка организации, полноценный раздел «Отчёты». Все четыре реализованы по-настоящему (не мокап) и покрыты тестами.

### Канбан: «автоматическое перетаскивание» = единый механизм для обеих причин движения
На уточняющий вопрос («визуальное отражение уже существующей серверной логики» vs «новый движок правил») заказчик выбрал оба варианта. Решение: карточка на канбане перемещается в новую колонку и визуально «переезжает» (FLIP-анимация по сдвигу `getBoundingClientRect()`) при **любом** изменении статуса — неважно, вызвано оно ручным перетаскиванием, существующей логикой (ответ клиента возвращает заявку из «Ждёт клиента» в «В работе», SLA-эскалации) или новым движком правил (см. ниже). Анимация реагирует на изменение позиции карточки между рендерами, а не на источник изменения — благодаря этому не пришлось заводить отдельный код для «ручного» и «автоматического» перемещения. Терминальные статусы (Закрыта/Отменена) на доску сознательно не выведены — канбан показывает работу в процессе, а не полную историю; они остаются доступны через список.

### Движок автоматизации статусов — одно правило, а не универсальный DSL
Вместо спекулятивного конструктора условий/действий реализован `AutomationRule` с одним типом триггера (`resolved_without_reply`), покрывающим уже существующее требование раздела 4.2 ТЗ («автозакрытие через N дней без ответа клиента», по умолчанию 3 дня) — которое до этого числилось в объёме Этапа 9. `trigger_type` — точка расширения на будущее (новые виды правил не потребуют новой миграции), но каждый новый вид триггера всё равно нуждается в коде обработки, тот же компромисс, что и `integration_settings.config`. Правило оценивается в воркере на том же тике, что и SLA-эскалации.

**Важный нюанс реализации:** `Ticket.resolved_at` фиксируется только при *первом* переводе в «Решена» и не обновляется при повторном решении после переоткрытия (см. решение про SLA при переоткрытии выше) — поэтому для проверки «сколько заявка находится в текущем статусе» движок automation берёт время последней записи в audit log (`status_changed` → `resolved`), а не `resolved_at` напрямую. Иначе повторно решённая после переоткрытия заявка с давним первым `resolved_at` закрылась бы автоматически немедленно.

### Отчёты — расширены за пределы ТЗ по прямому запросу
Раздел 9 ТЗ описывает 5 отчётов (SLA, отчёт клиенту, загрузка инженеров, поток заявок, CSAT); заказчик прямо попросил «существенно расширить... для полноценного понимания работы всей компании». Добавлены: возрастная структура открытого backlog (0–1/1–3/3–7/7+ дней — стандартная ITSM-метрика для здоровья очереди) и разрез потока по категориям в дополнение к каналам/организациям. Не добавлен reopen-rate (доля переоткрытых заявок) — посчитать его можно (через audit log), но решили не делать в этот проход без явного запроса, чтобы не разрастаться дальше; кандидат на будущее. Полноценный клиентский биллинг-отчёт за произвольный период (в отличие от текущего помесячного `/organizations/{id}/usage`) тоже не сделан — остаётся в объёме Этапа 7.

### Карточка организации — реального бага не было
Сообщение «не работает кнопка добавить организацию» разбирали: на момент проверки Docker-стек был выключен на машине заказчика, то есть проверялся статический мокап-артефакт, а не реальное приложение — в реальном приложении кнопка и раньше работала корректно (проверено вживую: создание организации прошло успешно). Реальным пробелом оказалось другое: у организации не было отдельной карточки (только плоский список), домены почты нельзя было редактировать после создания, ответственный менеджер не был виден/назначаем в UI, хотя поле `account_manager_id` в модели существовало с Этапа 1. Всё это закрыто новой страницей `/directory/organizations/:id`.

## Меню заявок в MAX, живая переписка, ответ на сообщение, уведомления (2026-07-31)

По запросу заказчика добавлены: окно выбора заявок в MAX-боте (посмотреть свои/создать новую/поднять старую), живое обновление переписки на карточке заявки, ответ на конкретное сообщение (цитирование) — и в MAX, и в карточке заявки сотрудника. Проверено на боевом токене; по ходу проверки заказчик указал на реальные проблемы, которые исправлены тут же.

### Живое обновление переписки — только карточка заявки сотрудника
Уточняющий вопрос («портал клиента» vs «карточка заявки у сотрудника») — заказчик выбрал карточку сотрудника (портал ещё не реализован, Этап 8). `TicketDetailPage.tsx`: `refetchInterval: 5_000` на запросе сообщений, отдельно от тикета (`30_000`, уже было с Этапа 3) — переписка обновляется чаще, потому что для активного диалога 30 секунд ощущаются как зависание.

### Ответ на сообщение (quoting) — общая для каналов схема, а не MAX-специфичная
`Message.reply_to_message_id` — self-FK, канало-независимое поле: на кого ссылается конкретное сообщение. Устанавливается явно через `MessageCreate`, а не выводится из канального заголовка (в отличие от `email_message_id`/`email_in_reply_to`, которые заполняются `email_channel.py` императивно после создания сообщения). У сотрудника в карточке заявки — кнопка «Ответить» на любом сообщении треда, цитата показывается инлайн (поиск по уже загруженному списку сообщений, без лишнего запроса).

Отдельно — `Message.max_message_id`: собственный идентификатор сообщения в MAX (`mid`), сохраняется и для входящих, и для исходящих сообщений. Нужен, чтобы reply работал в обе стороны: (а) когда клиент нативно отвечает на сообщение бота в MAX — по `link.mid` находим наше сообщение и проставляем `reply_to_message_id`; (б) когда инженер в карточке заявки нажимает «Ответить» на входящее MAX-сообщение — берём `max_message_id` этого сообщения и передаём в MAX как `link`, чтобы клиент увидел нативный ответ на своё сообщение, а не просто текст.

**Реальный формат `link` (проверено вживую, публичная документация поля не описывает):** `{"type": "reply", "message": {"mid": "...", "seq": ..., "text": "..."}, "sender": {...}, "chat_id": ...}` — вложенный объект, а не плоский `link.mid`, как можно было бы предположить. `_extract_link_mid` в `max_channel.py` разбирает вложенный вариант, с плоским как запасным (на случай другого формата у другого клиента MAX). Исходящий запрос (`max_client.send_message`, поле `link: {"type": "reply", "mid": ...}`) MAX принял и корректно связал сообщения — подтверждено тем, что при следующем чтении именно отправленного сообщения API вернул его уже с полным вложенным `link`.

### «Поднять старую» — новая заявка со связью, а не реюз закрытой
`CLOSED`/`CANCELLED` — терминальные статусы (`ALLOWED_TRANSITIONS`), назад не переводятся. Клиент выбирает закрытую заявку в «Мои заявки» → бот просит описать проблему → создаётся новая заявка с `parent_ticket_id`, указывающим на старую (поле в схеме существовало с Этапа 1, но без пути записи — теперь используется). `ChannelConversationState` получил `awaiting_revive_text`/`revive_parent_ticket_id` по аналогии с `awaiting_new_ticket_text`.

### Реальный баг, найденный при проверке: команда проглатывалась как текст заявки
Заказчик протестировал новое меню и написал: «работает, но теперь ничего не происходит и не приходит в SD». Разбор логов и БД: клиент второй раз открыл «Мои заявки» → выбрал уже закрытую тестовую заявку (`awaiting_revive_text = true`) → вместо описания проблемы написал `/start`, ожидая увидеть меню. Код (как и было изначально написано для `awaiting_new_ticket_text`) без разбора брал следующий текст как содержимое заявки — создалась настоящая заявка с темой `/start`, диалог переключился на неё, и все следующие сообщения («Тыры пыры», «пмро») ушли туда, а не в ожидаемую заявку. Заявку закрыл сам заказчик вручную, обнаружив её в очереди.

Исправлено: команды (`/start`, «мои заявки», «новая заявка» и их варианты) теперь всегда проверяются **до** веток `awaiting_new_ticket_text`/`awaiting_revive_text` и явно сбрасывают эти ожидания (`_cancel_pending_ticket_flow`) — команда больше не может быть случайно принята за текст заявки. Закреплено регресс-тестами (`test_start_command_cancels_pending_new_ticket_flow`, `test_my_tickets_command_cancels_pending_revive_flow`).

### Постоянное меню команд MAX (`/me/commands`) не отображается в клиенте
По документации `PATCH /me/commands` регистрирует список команд бота, показываемый в интерфейсе клиента (аналог `setMyCommands` в Telegram). Вызов реализован (`max_client.set_commands`, регистрируется один раз за процесс при первом опросе, `max_channel._ensure_commands_registered`) и **успешно принят API** (сервер вернул зарегистрированные команды в ответе) — но ни автодополнение по `/`, ни отдельная кнопка меню в использованном клиенте MAX не появились. Оставлено как есть (может заработать в другой версии клиента/платформе), но не единственный способ доступа к меню.

Заказчик подтвердил неудобство: «постоянно писать /start». Рабочее решение — кнопки главного меню («Мои заявки» / «Создать новую») теперь прикрепляются к **каждому ответу инженера клиенту** (`try_send_outbound`), а не только к приветствию. Это единственная точка обычного диалога, где боту гарантированно есть что отправить клиенту — в отличие от простой склейки ответа к заявке, которая намеренно остаётся без квитанции (чтобы не спамить на каждую реплику).

### Уведомления клиента: смена статуса и назначение исполнителя
По прямому запросу заказчика. `tickets_service.transition_status` вызывает `max_channel.notify_status_change` при любом переходе статуса (не дублирует сообщение при переходе в `CLOSED` — там уже есть отдельный текст в `request_csat`). `tickets_service.update_ticket` вызывает `max_channel.notify_assignment_change` при изменении `assigned_engineer_id`. Обе функции — no-op для каналов кроме MAX и при отсутствии сохранённого чата, по аналогии с `request_csat`; общая логика поиска состояния чата вынесена в `_find_chat_state` (убрал дублирование одного и того же запроса в четырёх местах).

### Молчаливая склейка сообщения тоже нуждалась в подтверждении и кнопках
После разбора описанного выше бага заказчик отдельно указал на саму причину, по которой баг вообще случился: «непонятно со стороны пользователя, как пользоваться ботом... как выйти из диалога заявки, как снова открыть список заявок». Действительно, обычное сообщение, которое молча приклеивается к активной заявке (`_append_message` в ветке `active_ticket_id`), раньше не получало никакого ответа от бота — у клиента не было визуального способа узнать, что сообщение дошло, ни кнопок, чтобы переключиться на другую заявку. Добавлено: `_acknowledge_gluing` — короткое «Принято по заявке OH-N.» с теми же кнопками главного меню, отправляется после каждого молчаливого приклеивания (все три ветки в `_handle_text`: единственная активная заявка, единственная открытая заявка, неоднозначный выбор). Кнопки меню теперь и в подтверждениях «Заявка создана»/«Переключено на» — раньше их не было.

### Кнопка «Закрыть заявку» — цепочка статусов, а не отдельный переход
По прямому запросу заказчика (клиент должен уметь закрыть свою заявку сам, не дожидаясь инженера). `CLOSED` достижим только из `RESOLVED` (`ALLOWED_TRANSITIONS`), поэтому `_close_via_client` не делает отдельный «клиентский» переход в обход правил, а прогоняет заявку по тем же одношаговым переходам, что и `transition_status` уже проверяет: `NEW/ASSIGNED/WAITING_* → IN_PROGRESS → RESOLVED → CLOSED`. Уточняющий вопрос — заказчик выбрал именно это (а не «отменить» или «кнопка только из Решена»), приняв, что клиент увидит уведомление о каждом промежуточном статусе плюс запрос CSAT, а не одно сообщение — так SLA/audit-бухгалтерия остаётся идентичной обычному закрытию инженером, без дублирования логики. Кнопка видна только пока заявка «закрываемая» (`_CLOSEABLE_STATUSES` = открытые статусы + `RESOLVED` — `RESOLVED` намеренно не входит в `OPEN_TICKET_STATUSES`, но закрыть его можно и нужно). Проверено вживую: заявка в статусе «Новая» после одного нажатия кнопки корректно прошла `new → in_progress → resolved → closed`, включая запрос оценки.
