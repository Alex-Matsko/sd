# Решения и уточнения к ТЗ

Дополняет [`TZ.md`](./TZ.md). Каждая запись — решение, принятое по ходу разработки там, где исходное ТЗ оставляло свободу трактовки. Новые решения дописывать в конец, не переписывать историю.

## Зафиксировано с заказчиком (2026-07-20)

### Номер заявки (Ticket ID)
Формат: `OH-<порядковый номер>`, например `OH-1042`. Сквозная нумерация по всей системе, без сброса по годам. Используется как тег `[#OH-1042]` в теме письма, в кнопках Telegram/MAX, в портале и в API.

### SLA/договор при отсутствии активного договора у организации
При создании заявки, если у организации нет активного договора: применяется тариф по умолчанию (базовый SLA), заявка создаётся и обрабатывается сразу. В карточке — пометка «нет активного договора» для диспетчера/руководителя, организационный вопрос решается параллельно, не блокируя работу по заявке.

### Биллинг на границе пакета часов
Если списание времени пересекает остаток пакета (например, остался 1 час, списано 3), запись делится пропорционально: часть — в счёт пакета, часть — по ставке сверх лимита. На уровне модели `TimeEntry` одна пользовательская запись времени может породить два расчётных отрезка (пакетный/сверхлимитный) для биллинга и отчётности, при этом пользователь видит и редактирует её как одну запись.

### SLA при переоткрытии заявки клиентом
Клиент отвечает на «Решённую» заявку в течение окна автозакрытия → заявка возвращается «В работе», исполнитель уведомлён. SLA по решению **не пересчитывается**: исходный результат (выполнено/нарушено) фиксируется как окончательный на момент первого перевода в «Решена». Работа после переоткрытия не создаёт новый дедлайн решения. Факт переоткрытия фиксируется в истории заявки (audit log) как есть, отдельная метрика reopen-rate — не в объёме v1, но поле для неё не блокируется на будущее.

## Предположения по умолчанию (озвучены, возражений не поступило — считаются принятыми)

- **Матрица Impact × Urgency**: стандартная ITIL-подобная таблица 3×3 → P1–P4, задаётся сид-данными, редактируется в настройках.
- **Порядок правил маршрутизации**: правило «организация → выделенный инженер» (более специфичное) применяется раньше правила «категория → группа»; при отсутствии совпадений — общая очередь диспетчера. Порядок — настраиваемое поле, не хардкод.
- **Бизнес-календари**: универсальная структура (окна по дням недели + справочник праздников РФ, редактируемый по годам). Сид-данные: 2–3 примера календаря (обычный офисный, продлённый, 24×7) с рабочими часами-заглушками — реальные часы для тарифов заказчик задаёт через настройки.
- **Сущность «Группа/команда» (Team)**: не описана явно в разделе 3 ТЗ, но нужна для маршрутизации по категории и для эскалации «руководителю группы». Вводится как отдельная сущность с полем «руководитель группы».
- **VIP-признак контакта**: в v1 — только визуальная метка для диспетчера/инженера, без автоматического влияния на приоритет или SLA. Поведение можно добавить позже без изменения схемы (поле уже булево).
- **Непривязанный контакт при автопривязке письма по домену организации**: заявка создаётся и обрабатывается сразу; контакт помечается «не подтверждён» до подтверждения диспетчером — не блокирует обработку заявки.
- **Мессенджер: клиент не ответил на запрос бота «к какой заявке относится сообщение»**, а написал следующее сообщение: ведём себя как в email-правиле — прикрепляем к последней активной заявке с пометкой для диспетчера.
- **Лимит размера вложения по умолчанию**: 25 МБ, настраиваемый параметр.

## Открытые вопросы (не блокируют Этап 1, решить до соответствующего этапа)

- Точные рабочие часы бизнес-календарей по факту (нужны реальные значения по тарифам заказчика) — до Этапа 3.
- Домен/поддомен и способ выпуска TLS-сертификата для портала клиента — до Этапа 8.
- Учётные данные интеграций: Telegram bot token, MAX bridge, Plusofon API-ключи, IMAP/SMTP почтового ящика поддержки — по мере входа в соответствующие этапы (4–6).

## Технические примечания по реализации Этапа 3 — SLA-движок (2026-07-22)

### Модель хранения дедлайнов
Срок решения хранится как абсолютный `sla_resolution_due_at`, а не как «оставшийся бюджет» — при постановке на паузу и снятии с паузы пересчитывается как `created_at + рабочее_время(бюджет_SLA + накопленная_пауза_в_рабочих_минутах)`. Пауза считается в рабочих минутах календаря (не в календарных), чтобы пауза на выходные не съедала рабочий бюджет. Один и тот же механизм пересчёта используется и при снятии с паузы, и при смене приоритета вручную.

### Фиксация результата (met/breached)
`sla_reaction_met` и `sla_resolution_met` — тройное состояние (`NULL` = ещё не решено, `true`/`false` = зафиксировано). Фиксируются один раз: по реакции — первым исходящим сообщением инженера или сработавшей эскалацией 100%; по решению — первым переводом в «Решена» или эскалацией 100%. После фиксации значение не пересчитывается (согласуется с более ранним решением про SLA при переоткрытии). Смена приоритета обнуляет `met=false`, если новый дедлайн ещё не наступил (иначе нарушение, уже случившееся по старому таймеру, осталось бы «зависшим» несправедливо), но никогда не трогает уже свершившийся положительный результат.

### Эскалации 75%/100%
Отдельный процесс-воркер (`app/worker.py`, контейнер `worker` в compose) раз в `WORKER_INTERVAL_SECONDS` (по умолчанию 60 с) сканирует открытые заявки без зафиксированного результата. На 75% бюджета — уведомление исполнителю (или руководителю группы, если не назначен); на 100% — фиксация нарушения и уведомление исполнителю **и** руководителю группы одновременно. Разовые метки `sla_*_warned_at`/`sla_*_escalated_at` на заявке гарантируют, что каждое уведомление уходит ровно один раз; сбрасываются при пересчёте по смене приоритета.

### Уведомления — только in-app на этом этапе
Добавлена таблица `notifications` и раздел в topbar (колокольчик, список, «прочитать все»). Доставка в личный Telegram инженера — по ТЗ раздел 8, реализуется в Этапе 4 вместе с остальной телеграм-интеграцией; модель уведомлений уже не потребует миграции под это.

### Обратная совместимость: заявки, созданные до Этапа 3
Колонки SLA существовали как nullable ещё с Этапа 1 (расчёт на будущее движка), поэтому заявки, созданные в Этапах 1–2, имеют `sla_reaction_due_at`/`sla_resolution_due_at = NULL`. При каждом старте `app.seed` теперь докатывает дедлайны для таких заявок — но **только если заявка ещё не продвинулась** (нет ни первого ответа, ни решения): для уже отвеченных/решённых до появления движка результат не переоценивается задним числом (не «придумываем» нарушение/выполнение по правилу, которое в момент события не действовало). Такие заявки остаются в состоянии «без SLA» — по замыслу, это не баг, а сознательная граница ответственности движка.

### Гонка контейнеров при старте
`worker` и `nginx` теперь зависят от `app` через Docker healthcheck (`condition: service_healthy`), а не просто от готовности `db` — иначе воркер иногда успевал обратиться к БД до применения миграций `app`-контейнером (замечено в разработке: первый цикл воркера падал на `UndefinedColumn`, второй проходил штатно благодаря ретраю, но само по себе полагаться на ретрай — не решение).

## Технические примечания по реализации Этапа 4 — Email-канал (2026-07-22)

### Универсальные настройки каналов вместо `.env`
По запросу заказчика учётные данные интеграций (IMAP/SMTP сейчас; Telegram bot token, MAX bridge, Plusofon API-ключи на будущих этапах) вынесены из `.env` в БД и редактируются в интерфейсе (Настройки → Каналы, раздел 8 ТЗ). Реализовано одной универсальной таблицей `integration_settings` (канал → JSON `config` + JSON `secrets_encrypted`), а не отдельной типизированной моделью на каждый канал — новый канал не требует новой миграции, только согласование ключей конфига на уровне приложения. Секреты шифруются `Fernet` (ключ `SETTINGS_ENCRYPTION_KEY` в `.env` — это единственное, что осталось «инфраструктурным» и не переехало в БД, т.к. без него сами секреты не расшифровать) и никогда не отдаются через API в открытом виде — только флаг, какие ключи заданы. Frontend показывает пароль/токен как пустое поле «оставьте пустым, чтобы не менять» плюс кнопку «Очистить», а не сам секрет.

### Приоритет привязки входящего письма к заявке
Реализовано строго по разделу 2.3: (1) заголовки In-Reply-To/References против `Message.email_message_id`, сохранённого на предыдущих исходящих письмах этой же заявки; (2) тег `[#OH-<номер>]` в теме; (3) единственная открытая заявка контакта; (4) несколько открытых заявок без совпадения по заголовкам/тегу → последняя активная (по `updated_at`, с `id` как детерминированным тай-брейкером — `now()` в Postgres одинаков для всех операторов одной транзакции, поэтому только timestamp недостаточен) с автоматической внутренней заметкой-пометкой для диспетчера; (5) открытых заявок нет → новая заявка. Новая заявка от письма создаётся с типом Incident и приоритетом P3 (ручной, с причиной «автоматически создано по email») — реальные Impact/Urgency клиент по почте не указывает, дальнейшую классификацию делает диспетчер/инженер.

### Очередь «Неизвестные»
Письма с адреса, не совпадающего ни с одним контактом и не относящегося к зарегистрированному корпоративному домену организации (включая все публичные домены из `PublicEmailDomain`), попадают в заявки организации-заглушки «Неизвестные» (создаётся лениво при первом обращении, ищется по имени — тот же приём, что и зарезервированный `code` тарифа по умолчанию). Контакт создаётся с `is_confirmed=false`. Полноценный UI «перепривязать контакт и его заявки к другой организации» не реализован в этом этапе — диспетчер видит такие заявки через фильтр по организации «Неизвестные» в общей очереди; отдельный экран разбора — кандидат на один из следующих этапов, если появится такая необходимость.

### Обработка ошибок при IMAP-опросе
Письмо считается обработанным, как только оно прочитано через `FETCH RFC822` (IMAP помечает `\Seen` автоматически) — даже если разбор/создание заявки после этого упало с исключением. Альтернатива («не помечать как прочитанное при ошибке») ведёт к бесконечному повтору одного и того же письма при системной ошибке разбора и риску дублирования уже частично созданных сущностей. Каждая ошибка полностью логируется для последующего ручного разбора; это компромисс, осознанно принятый для v1.

### Что не реализовано в этом проходе Этапа 4
ТЗ относит к Этапу 4 также «уведомления инженерам в Telegram» — это осталось не сделанным (нет Telegram-бота, нет доставки уведомлений о новых заявках/эскалациях в личный чат инженера). Инфраструктура настроек уже готова к этому: в `integration_settings` заведена заглушка канала `telegram` (переключатель «включён», без полей конфигурации), форма появится вместе с реализацией самого бота.

## Технические примечания по реализации Этапа 5 — канал MAX (2026-07-22)

### Референсной реализации не было — разработка с нуля
Ранее упомянутый в ТЗ рабочий MAX-бридж заказчика (long polling + SQLite mapping) в итоге так и не был доведён до конца и не был предоставлен как референс. Канал реализован с нуля по официальной документации `dev.max.ru/docs-api`, полученной через веб-поиск на момент разработки (2026-07-22) — **без доступа к боевому токену бота для проверки реальных ответов сервера**. Зафиксированные из документации факты:

- Домен API: `platform-api2.max.ru` (старый `platform-api.max.ru` выводится из эксплуатации к 2026-07-19 — уже пройдено на момент разработки, поэтому используется только новый).
- Авторизация: заголовок `Authorization: <токен>` без префикса `Bearer`.
- Приём: `GET /updates` (long polling, поля `marker`/`timeout`/`limit`), продакшен официально рекомендует webhook, но клиент прямо просил long polling (как и было в его прежнем бридже) — самостоятельный TLS-эндпоинт с публичным сертификатом не нужен, что соответствует общему принципу ТЗ «self-hosted без белого IP».
- Отправка: `POST /messages` (`chat_id`, `text`, вложения через `attachments`, кнопки — через `inline_keyboard`).
- Структура события: `update_type` (`message_created`/`message_callback`/`bot_started`/…), сообщение — `sender.user_id`, `recipient.chat_id`, `body.text`.

Разбор входящих событий (`_extract_incoming` в `app/services/max_channel.py`) сознательно защитный — все обращения к полям через `.get()` с проверкой на `None`, а не через прямой доступ по ключу: если реальный сервер вернёт другую форму данных, обработчик залогирует и пропустит событие вместо падения. **Перед вводом в эксплуатацию обязательно нужно завести тестового бота и сверить реальные структуры событий с кодом** — вся точка входа для правок сосредоточена в этой одной функции.

### Маркер long polling хранится в БД, не в памяти процесса
`marker` (курсор `/updates`) сохраняется в `integration_settings.config._marker` после каждого опроса — иначе перезапуск воркера заново получал бы уже обработанные события. Побочный эффект: если администратор пересохранит настройки канала MAX через интерфейс, маркер будет затёрт (форма отправляет весь `config` целиком) и бот один раз перечитает недавние события повторно. Это осознанно принятый компромисс (редкое действие администратора, ограниченный и не разрушительный повтор) в обмен на простоту — не заводили отдельное хранилище только ради этого поля.

### MAX-опрос — в отдельном потоке воркера, не в общем тике
`GET /updates` блокируется на сервере до `timeout` секунд (до 90). Если бы этот вызов стоял в общем цикле воркера рядом с SLA-эскалациями и опросом почты (`app/worker.py`), долгий опрос MAX откладывал бы SLA-эскалации на то же время. Поэтому MAX-поллинг вынесен в отдельный `threading.Thread`, независимый от основного тика; общий цикл (SLA раз в минуту + email по своему интервалу) не блокируется.

### Правила склейки диалога и очередь «Неизвестные» — идентичны email
Одна открытая заявка — сообщение в неё; несколько — бот показывает кнопки списком (плюс «Создать новую»), при ответе обычным текстом вместо кнопки — привязка к последней активной с внутренней пометкой для диспетчера (тот же принцип, что и в письмах, см. примечания Этапа 4). Активная заявка контакта хранится в новой таблице `channel_conversation_states` (одна запись на пару канал+внешний ID пользователя) и держится, пока клиент не переключится через «Мои заявки» или заявка не перестанет быть открытой. Явное создание новой заявки — командой/кнопкой «Создать новую» — переводит диалог в режим ожидания следующего сообщения как описания проблемы. Неопознанные отправители (MAX ID не привязан ни к одному контакту) уходят в ту же организацию-заглушку «Неизвестные», что и email (`app/services/unknown_queue.py`, вынесен в общий модуль вместо дублирования).

### CSAT: добавлено раньше срока (Этап 9 по плану), т.к. это часть функций бота
Раздел 2.1/2.2 ТЗ прямо перечисляет «оценка после закрытия (1–5)» как функцию бота — поэтому запрос оценки (кнопки 1–5) и приём ответа реализованы уже сейчас: при переводе заявки в «Закрыта» (`services/tickets.transition_status`) для заявок канала MAX отправляется запрос, ответ по кнопке фиксируется в `Ticket.csat_rating`/`csat_rated_at` (первая оценка финальна, повторные попытки игнорируются). Полноценная отчётность CSAT (сводные показатели, разрез по инженерам/организациям) остаётся в Этапе 9 — колонки уже есть, повторной миграции не потребуется.

### Вложения от клиента через MAX — только при наличии прямой ссылки
MAX отдаёт вложения как типизированные payload'ы; официально описанный способ получения файла по токену через отдельный запрос не проверялся вживую. Вложение сохраняется, только если в его payload сразу есть `url` для скачивания (по документации это в целом относится к изображениям) — иначе событие логируется и пропускается с пометкой «требует проверки на боевом токене», без попытки угадать неподтверждённый API вызова. Исходящие вложения (файл от инженера клиенту в MAX) в этом проходе не реализованы вовсе.

## Проверка канала MAX на боевом токене (2026-07-31)

Заказчик предоставил реальный токен своего бота. Проверка вживую вскрыла и позволила закрыть три расхождения с тем, что было написано по одной только публичной документации (см. примечания по Этапу 5 выше) — обновляю здесь итоговое состояние.

### Сертификат MAX подписан российским государственным УЦ — обычные образы Linux ему не доверяют
`platform-api2.max.ru` отдаёт цепочку, подписанную `Russian Trusted Sub CA` → `Russian Trusted Root CA` (Минцифры России) — это не входит в стандартный набор доверенных корневых сертификатов Mozilla/Debian, на котором собран `python:3.12-slim`. Без этого сертификата ЛЮБОЕ обращение к MAX API падает с `SSL: CERTIFICATE_VERIFY_FAILED`, независимо от корректности токена или кода. Это не ограничение среды разработки — то же самое будет на любой не-российской по умолчанию системе, включая продовую ВМ заказчика, если на ней не установлен этот корневой сертификат отдельно от общей системы.

Решение: корневой сертификат (`backend/certs/russian-trusted-root-ca.pem`, официально выпущен Минцифры 2022 г., до 2032 г.) закоммичен в репозиторий и устанавливается в образ на этапе сборки (`Dockerfile`: `COPY` + `update-ca-certificates`) — воспроизводимо, без обращения к внешним источникам при каждой сборке. Сертификат получен и проверен через публичный GitHub-репозиторий (независимое зеркало официального сертификата), затем подтверждён вручную через `openssl s_client` — сервер сам присылает промежуточный Sub CA в хендшейке, поэтому в доверенных достаточно только корневого.

### `httpx` не использует системное хранилище сертификатов ОС по умолчанию
Даже после установки российского сертификата в систему запросы `httpx` (используется в `max_client.py`) продолжали падать с той же ошибкой — потому что `httpx` при `verify=True` (значение по умолчанию) проверяет сертификат по **своему собственному** пакету `certifi` (курируемый список Mozilla), а не по системному `/etc/ssl/certs/ca-certificates.crt`, который обновляет `update-ca-certificates`. Это общая особенность `httpx`/`requests`, а не что-то специфичное для этого проекта — но именно из-за неё установка сертификата в ОС сама по себе ничего не чинит для Python-кода на `httpx`. Решение: `max_client.py` явно передаёт `verify="/etc/ssl/certs/ca-certificates.crt"` в оба `httpx.Client(...)` (с проверкой `os.path.exists` и откатом на стандартное поведение `httpx`, если файла нет — например, при локальном запуске вне Docker).

### `chat_id` в `POST /messages` — параметр запроса, а не поле JSON-тела
Публичная документация (и, соответственно, первоначальная реализация) предполагала `{"text": ..., "chat_id": ...}` в теле запроса. На боевом токене это стабильно возвращало `400 {"code":"proto.payload","message":"Unknown recipient"}` — ответ, который выглядит как «неизвестный получатель», но на деле означает «получатель не там, где я его ищу»: реальный API ожидает `chat_id` как query-параметр (`POST /messages?chat_id=...`), а тело запроса содержит только содержимое сообщения (`text`, `attachments`). Исправлено в `max_client.send_message`; поведение зафиксировано регресс-тестами на `httpx.MockTransport` (`tests/test_max_client.py`), чтобы это не могли случайно отменить в будущем.

**Итог:** после этих трёх правок полный цикл проверен вживую от начала до конца — входящее сообщение в реальном боте создало настоящую заявку (OH-917) с корректным разбором отправителя, а исходящий ответ инженера дошёл до реального MAX-аккаунта (подтверждено эхом от API с именем бота отправителя). Формат `Update`/`Message`, который был описан как «неподтверждённый» в примечаниях по Этапу 5, теперь подтверждён 1:1 с реальным API для `message_created` — по прежнему не проверены только вложения и `message_callback`/`bot_started`, они не встречались в реальном трафике при этой проверке.

## Внеплановые доработки по запросу заказчика (2026-07-31)

Заказчик посмотрел визуальный мокап интерфейса (сгенерированный как референс на основе уже собранного дизайна) и запросил доработки текущего рабочего интерфейса вне очереди этапов ТЗ: канбан-доска очереди, движок автоматизации статусов, углублённая карточка организации, полноценный раздел «Отчёты». Все четыре реализованы по-настоящему (не мокап) и покрыты тестами.

### Канбан: «автоматическое перетаскивание» = единый механизм для обеих причин движения
На уточняющий вопрос («визуальное отражение уже существующей серверной логики» vs «новый движок правил») заказчик выбрал оба варианта. Решение: карточка на канбане перемещается в новую колонку и визуально «переезжает» (FLIP-анимация по сдвигу `getBoundingClientRect()`) при **любом** изменении статуса — неважно, вызвано оно ручным перетаскиванием, существующей логикой (ответ клиента возвращает заявку из «Ждёт клиента» в «В работе», SLA-эскалации) или новым движком правил (см. ниже). Анимация реагирует на изменение позиции карточки между рендерами, а не на источник изменения — благодаря этому не пришлось заводить отдельный код для «ручного» и «автоматического» перемещения. Терминальные статусы (Закрыта/Отменена) на доску сознательно не выведены — канбан показывает работу в процессе, а не полную историю; они остаются доступны через список.

### Движок автоматизации статусов — одно правило, а не универсальный DSL
Вместо спекулятивного конструктора условий/действий реализован `AutomationRule` с одним типом триггера (`resolved_without_reply`), покрывающим уже существующее требование раздела 4.2 ТЗ («автозакрытие через N дней без ответа клиента», по умолчанию 3 дня) — которое до этого числилось в объёме Этапа 9. `trigger_type` — точка расширения на будущее (новые виды правил не потребуют новой миграции), но каждый новый вид триггера всё равно нуждается в коде обработки, тот же компромисс, что и `integration_settings.config`. Правило оценивается в воркере на том же тике, что и SLA-эскалации.

**Важный нюанс реализации:** `Ticket.resolved_at` фиксируется только при *первом* переводе в «Решена» и не обновляется при повторном решении после переоткрытия (см. решение про SLA при переоткрытии выше) — поэтому для проверки «сколько заявка находится в текущем статусе» движок automation берёт время последней записи в audit log (`status_changed` → `resolved`), а не `resolved_at` напрямую. Иначе повторно решённая после переоткрытия заявка с давним первым `resolved_at` закрылась бы автоматически немедленно.

### Отчёты — расширены за пределы ТЗ по прямому запросу
Раздел 9 ТЗ описывает 5 отчётов (SLA, отчёт клиенту, загрузка инженеров, поток заявок, CSAT); заказчик прямо попросил «существенно расширить... для полноценного понимания работы всей компании». Добавлены: возрастная структура открытого backlog (0–1/1–3/3–7/7+ дней — стандартная ITSM-метрика для здоровья очереди) и разрез потока по категориям в дополнение к каналам/организациям. Не добавлен reopen-rate (доля переоткрытых заявок) — посчитать его можно (через audit log), но решили не делать в этот проход без явного запроса, чтобы не разрастаться дальше; кандидат на будущее. Полноценный клиентский биллинг-отчёт за произвольный период (в отличие от текущего помесячного `/organizations/{id}/usage`) тоже не сделан — остаётся в объёме Этапа 7.

### Карточка организации — реального бага не было
Сообщение «не работает кнопка добавить организацию» разбирали: на момент проверки Docker-стек был выключен на машине заказчика, то есть проверялся статический мокап-артефакт, а не реальное приложение — в реальном приложении кнопка и раньше работала корректно (проверено вживую: создание организации прошло успешно). Реальным пробелом оказалось другое: у организации не было отдельной карточки (только плоский список), домены почты нельзя было редактировать после создания, ответственный менеджер не был виден/назначаем в UI, хотя поле `account_manager_id` в модели существовало с Этапа 1. Всё это закрыто новой страницей `/directory/organizations/:id`.

## Меню заявок в MAX, живая переписка, ответ на сообщение, уведомления (2026-07-31)

По запросу заказчика добавлены: окно выбора заявок в MAX-боте (посмотреть свои/создать новую/поднять старую), живое обновление переписки на карточке заявки, ответ на конкретное сообщение (цитирование) — и в MAX, и в карточке заявки сотрудника. Проверено на боевом токене; по ходу проверки заказчик указал на реальные проблемы, которые исправлены тут же.

### Живое обновление переписки — только карточка заявки сотрудника
Уточняющий вопрос («портал клиента» vs «карточка заявки у сотрудника») — заказчик выбрал карточку сотрудника (портал ещё не реализован, Этап 8). `TicketDetailPage.tsx`: `refetchInterval: 5_000` на запросе сообщений, отдельно от тикета (`30_000`, уже было с Этапа 3) — переписка обновляется чаще, потому что для активного диалога 30 секунд ощущаются как зависание.

### Ответ на сообщение (quoting) — общая для каналов схема, а не MAX-специфичная
`Message.reply_to_message_id` — self-FK, канало-независимое поле: на кого ссылается конкретное сообщение. Устанавливается явно через `MessageCreate`, а не выводится из канального заголовка (в отличие от `email_message_id`/`email_in_reply_to`, которые заполняются `email_channel.py` императивно после создания сообщения). У сотрудника в карточке заявки — кнопка «Ответить» на любом сообщении треда, цитата показывается инлайн (поиск по уже загруженному списку сообщений, без лишнего запроса).

Отдельно — `Message.max_message_id`: собственный идентификатор сообщения в MAX (`mid`), сохраняется и для входящих, и для исходящих сообщений. Нужен, чтобы reply работал в обе стороны: (а) когда клиент нативно отвечает на сообщение бота в MAX — по `link.mid` находим наше сообщение и проставляем `reply_to_message_id`; (б) когда инженер в карточке заявки нажимает «Ответить» на входящее MAX-сообщение — берём `max_message_id` этого сообщения и передаём в MAX как `link`, чтобы клиент увидел нативный ответ на своё сообщение, а не просто текст.

**Реальный формат `link` (проверено вживую, публичная документация поля не описывает):** `{"type": "reply", "message": {"mid": "...", "seq": ..., "text": "..."}, "sender": {...}, "chat_id": ...}` — вложенный объект, а не плоский `link.mid`, как можно было бы предположить. `_extract_link_mid` в `max_channel.py` разбирает вложенный вариант, с плоским как запасным (на случай другого формата у другого клиента MAX). Исходящий запрос (`max_client.send_message`, поле `link: {"type": "reply", "mid": ...}`) MAX принял и корректно связал сообщения — подтверждено тем, что при следующем чтении именно отправленного сообщения API вернул его уже с полным вложенным `link`.

### «Поднять старую» — новая заявка со связью, а не реюз закрытой
`CLOSED`/`CANCELLED` — терминальные статусы (`ALLOWED_TRANSITIONS`), назад не переводятся. Клиент выбирает закрытую заявку в «Мои заявки» → бот просит описать проблему → создаётся новая заявка с `parent_ticket_id`, указывающим на старую (поле в схеме существовало с Этапа 1, но без пути записи — теперь используется). `ChannelConversationState` получил `awaiting_revive_text`/`revive_parent_ticket_id` по аналогии с `awaiting_new_ticket_text`.

### Реальный баг, найденный при проверке: команда проглатывалась как текст заявки
Заказчик протестировал новое меню и написал: «работает, но теперь ничего не происходит и не приходит в SD». Разбор логов и БД: клиент второй раз открыл «Мои заявки» → выбрал уже закрытую тестовую заявку (`awaiting_revive_text = true`) → вместо описания проблемы написал `/start`, ожидая увидеть меню. Код (как и было изначально написано для `awaiting_new_ticket_text`) без разбора брал следующий текст как содержимое заявки — создалась настоящая заявка с темой `/start`, диалог переключился на неё, и все следующие сообщения («Тыры пыры», «пмро») ушли туда, а не в ожидаемую заявку. Заявку закрыл сам заказчик вручную, обнаружив её в очереди.

Исправлено: команды (`/start`, «мои заявки», «новая заявка» и их варианты) теперь всегда проверяются **до** веток `awaiting_new_ticket_text`/`awaiting_revive_text` и явно сбрасывают эти ожидания (`_cancel_pending_ticket_flow`) — команда больше не может быть случайно принята за текст заявки. Закреплено регресс-тестами (`test_start_command_cancels_pending_new_ticket_flow`, `test_my_tickets_command_cancels_pending_revive_flow`).

### Постоянное меню команд MAX (`/me/commands`) не отображается в клиенте
По документации `PATCH /me/commands` регистрирует список команд бота, показываемый в интерфейсе клиента (аналог `setMyCommands` в Telegram). Вызов реализован (`max_client.set_commands`, регистрируется один раз за процесс при первом опросе, `max_channel._ensure_commands_registered`) и **успешно принят API** (сервер вернул зарегистрированные команды в ответе) — но ни автодополнение по `/`, ни отдельная кнопка меню в использованном клиенте MAX не появились. Оставлено как есть (может заработать в другой версии клиента/платформе), но не единственный способ доступа к меню.

Заказчик подтвердил неудобство: «постоянно писать /start». Рабочее решение — кнопки главного меню («Мои заявки» / «Создать новую») теперь прикрепляются к **каждому ответу инженера клиенту** (`try_send_outbound`), а не только к приветствию. Это единственная точка обычного диалога, где боту гарантированно есть что отправить клиенту — в отличие от простой склейки ответа к заявке, которая намеренно остаётся без квитанции (чтобы не спамить на каждую реплику).

### Уведомления клиента: смена статуса и назначение исполнителя
По прямому запросу заказчика. `tickets_service.transition_status` вызывает `max_channel.notify_status_change` при любом переходе статуса (не дублирует сообщение при переходе в `CLOSED` — там уже есть отдельный текст в `request_csat`). `tickets_service.update_ticket` вызывает `max_channel.notify_assignment_change` при изменении `assigned_engineer_id`. Обе функции — no-op для каналов кроме MAX и при отсутствии сохранённого чата, по аналогии с `request_csat`; общая логика поиска состояния чата вынесена в `_find_chat_state` (убрал дублирование одного и того же запроса в четырёх местах).

## Канал Telegram, вынесение общей логики ботов, контейнеризация фронтенда, сопоставление контактов (2026-07-31)

По запросу заказчика («делаем такой же бот для телеграма») реализован второй мессенджер-канал, зеркальный MAX по функциональности. Заказчик предоставил реальный токен бота — проверено вживую так же, как MAX.

### Telegram Bot API оказался значительно предсказуемее MAX
В отличие от MAX (публичная документация которого разошлась с реальным API минимум трижды — см. выше), официальный Bot API Telegram подтвердился 1:1 с документацией на всех проверенных вживую пунктах: `chat_id` и `reply_to_message_id` — действительно поля JSON-тела (не query-параметр, как у MAX), ответ на сообщение — плоское целое `reply_to_message_id` (не вложенный объект `link`, как у MAX), сертификат сервера — из обычного публичного набора доверия (без вопроса с российским корневым УЦ). Единственное специфичное для Telegram: `answerCallbackQuery` нужно вызывать на каждый `callback_query`, иначе кнопка в клиенте остаётся с крутящимся индикатором загрузки (чисто косметически, без функциональных последствий, если пропустить, но код это делает всегда).

### `setMyCommands` в Telegram реально работает — в отличие от `/me/commands` у MAX
Постоянное меню команд (`/start`, `/tickets`, `/new` — значок «/» у поля ввода) подтверждено заказчиком вживую как рабочее. Поэтому кнопки главного меню («Мои заявки»/«Создать новую»), которые для MAX дублируются на каждом ответе инженера и на каждой склейке сообщения (см. выше, единственный способ добраться до меню без рабочего `/me/commands`), в Telegram-канале **не дублируются** — по прямому запросу заказчика («в телеграме есть нормальное меню, не нужно дублировать»). Оставлена только кнопка «Закрыть заявку» (`_close_button_for`) — она привязана к конкретной заявке и не может быть статической командой меню.

### `messenger_common.py` — общий слой между MAX и Telegram
Оба канала используют идентичные бизнес-правила (метки статусов, набор «закрываемых» статусов, цепочка клиентского закрытия `IN_PROGRESS → RESOLVED → CLOSED`, русские тексты команд бота) — вынесены в отдельный модуль, чтобы не расходились при будущих правках. Разбор формата обновлений, отправка сообщений и вся оркестрация диалога намеренно **не** обобщены в единый адаптер — формат MAX и Telegram отличается ровно настолько (see выше), что общий транспортный слой обошёлся бы дороже, чем два похожих файла `max_channel.py`/`telegram_channel.py`. Рефакторинг `max_channel.py` под общий модуль сделан как чистый перенос без изменения логики — прогон полного набора тестов после рефакторинга ничего не показал.

### Сопоставление контактов между каналами: сначала блокирующий вариант, потом откат на неблокирующий
Заказчик спросил, как сопоставить одного и того же клиента, писавшего и в MAX, и в Telegram, чтобы показывать ему одну и ту же историю заявок. Первая реализация запрашивала телефон **перед** созданием заявки при первом обращении с любого канала — и была отменена до коммита: это добавляло лишний шаг абсолютно всем новым клиентам (подавляющее большинство которых не имеют дублей), ломая уже проверенный вживую сценарий «первое сообщение — сразу заявка» почти во всех существующих тестах (~40 точек вызова в обоих наборах тестов ожидали немедленного создания). Обнаружено на этапе тестов, до того как попало в прод — сам факт, что придётся переписать почти весь набор тестов под новое поведение, был сигналом, что решение неверное.

Финальный вариант — необязательный, по инициативе клиента: команда «связать телефон» (`LINK_PHONE_COMMANDS`) переводит бота в режим ожидания номера; при совпадении с уже существующим контактом (`messenger_common.find_contact_by_phone`, сравнение по последним 10 цифрам, чтобы не зависеть от формата `+7`/`8`/`7`/пробелов) — вызывается `merge_contacts` и текущий диалог переключается на найденный контакт; без совпадения — номер просто сохраняется на текущем контакте для будущих попыток. Подсказка про команду сама появляется в подтверждении создания заявки, только если контакт ещё не подтверждён (`is_confirmed=False`).

`merge_contacts` — общая функция для двух путей: автоматического (через «связать телефон») и ручного (кнопка «Объединить» в разделе Контакты → `POST /contacts/{id}/merge`, роль диспетчер и выше). Переносит заявки, сообщения и состояния диалога с одного контакта на другой, копирует `max_id`/`telegram_id` только если у цели их ещё нет (не затирает уже привязанный канал), затем удаляет исходный контакт. **Важный нюанс SQLAlchemy**: `Contact.phones`/`Contact.emails` объявлены с `cascade="all, delete-orphan"` — простого переноса `phone.contact_id = новый_id` недостаточно, ORM отслеживает «осиротевшие» объекты по членству в коллекции `from_contact.phones`, а не по значению внешнего ключа; без явного `from_contact.phones.remove(phone)` / `into_contact.phones.append(phone)` последующий `db.delete(from_contact)` каскадно удалял только что перенесённый телефон. Поймано тестом (`test_merge_contacts_moves_phone_and_email`), а не проверкой в проде.

## Завершение Этапа 4: уведомления инженерам в Telegram (2026-07-31)

Раздел 8 ТЗ: «Уведомления инженерам: в интерфейсе (websocket) + в Telegram (личный бот-канал системы, инженер привязывает свой TG в профиле)». Реализована Telegram-часть и привязка; websocket-часть в этот проход не входит (см. ниже).

### Самостоятельная привязка через код, а не отдельный бот
«Личный бот-канал системы» — это тот же самый бот `telegram_channel.py`, который уже обслуживает клиентов, а не второй отдельный бот: заводить и поддерживать второй токен ради внутренних уведомлений было бы лишней инфраструктурой без выигрыша — клиент и инженер это разные Telegram-пользователи, пишущие боту каждый в своём приватном диалоге, смешения переписки не возникает. Привязка — по короткому одноразовому коду: новая страница «Профиль» (топбар → аватар пользователя) выпускает код через `POST /auth/me/telegram-link-code` (15 минут жизни, `User.telegram_link_code`/`telegram_link_code_expires_at`), инженер отправляет боту `/link <код>`. Разбор `/link` в `telegram_channel.handle_update` стоит **раньше** обычного разбора клиентского диалога (`_try_link_engineer`, до `_resolve_contact`) — иначе код по ошибке ушёл бы в создание заявки от имени случайного контакта, той же природы баг, что и раньше с `/start`, проглатываемым как текст заявки (см. выше), только на этот раз для другого типа сущности (`User`, не `Contact`) — исправлено сразу на этапе проектирования, не постфактум.

### Доставка — довесок к уже существующему триггеру, не новый
Единственный существующий источник уведомлений инженерам — эскалации SLA (`sla.py::_notify`, 75%/100% по разделу 4.3 ТЗ). Новых типов уведомлений не придумано: `_notify` теперь просто дублирует то же сообщение (тот же `title`) в Telegram тем получателям, у кого `User.telegram_id` заполнен, если канал Telegram включён в настройках — `_notify_telegram` молча ничего не делает для остальных (нет TG, канал выключен), симметрично тому, как уже устроены `request_csat`/`notify_status_change` в клиентских каналах. Отложенный импорт `telegram_channel`/`telegram_client` внутри функции обязателен: `sla.py` импортируется `tickets.py` на уровне модуля, а `telegram_channel.py` → `messenger_common.py` → `tickets_service` — модульный импорт `sla → telegram_channel` дал бы цикл.

### Websocket остаётся отложенным
ТЗ прямо требует websocket для внутриинтерфейсных уведомлений; сейчас это по-прежнему REST-опрос раз в 30 секунд (`NotificationBell`, без изменений в этом проходе). Поднимать websocket/pub-sub (и вероятно Redis под него, как отмечено в README ещё с Этапа 1) — отдельная по объёму задача, не обязательная для того, чтобы уведомления в Telegram заработали; отмечаю как осознанно оставленный долг, а не забытый пункт ТЗ.

### Контейнеризация фронтенда — раньше не было вообще
Заказчик спросил, по какому адресу открывать панель, и почему она не в контейнере — оказалось, что `README.md` вводил в заблуждение («API и SPA доступны через nginx: http://localhost:8080»), а реально `nginx/nginx.conf` только проксировал API, и единственный рабочий способ запустить панель был `npm run dev` на хосте. Добавлены `frontend/Dockerfile` (многоступенчатая сборка: `node:20-alpine` → `nginx:1.27-alpine` отдаёт `dist/` статикой) и сервис `frontend` в `docker-compose.yml` на отдельном порту (`FRONTEND_PORT`, по умолчанию 8081).

**Почему на отдельном порту, а не на одном с API**: роутеры backend висят на корневых путях без префикса `/api` (`/tickets`, `/users`, `/organizations`...) — это ровно те же пути, что и клиентские маршруты SPA (`/tickets/123` — и API-эндпоинт, и адрес карточки заявки в браузере). Развести их на одном порту потребовало бы либо вводить `/api`-префикс во все роутеры backend (более инвазивный рефакторинг, не в объёме этой правки), либо различать запросы по заголовкам (`Accept`/XHR-эвристики, ненадёжно). Разнесение по портам полностью убирает коллизию: `VITE_API_BASE_URL` — build arg, вшивается в JS-бандл при сборке образа `frontend` (через `.env.production`, а не переменную окружения контейнера — Vite читает переменные `VITE_*` на этапе сборки, а бандл выполняется в браузере пользователя, не в Docker-сети). Проверено вживую через Playwright с реальным JWT (выпущен напрямую через `create_access_token`, без необходимости менять пароль администратора) — очередь заявок загрузилась с реальными данными, ошибок в консоли нет.

### Молчаливая склейка сообщения тоже нуждалась в подтверждении и кнопках
После разбора описанного выше бага заказчик отдельно указал на саму причину, по которой баг вообще случился: «непонятно со стороны пользователя, как пользоваться ботом... как выйти из диалога заявки, как снова открыть список заявок». Действительно, обычное сообщение, которое молча приклеивается к активной заявке (`_append_message` в ветке `active_ticket_id`), раньше не получало никакого ответа от бота — у клиента не было визуального способа узнать, что сообщение дошло, ни кнопок, чтобы переключиться на другую заявку. Добавлено: `_acknowledge_gluing` — короткое «Принято по заявке OH-N.» с теми же кнопками главного меню, отправляется после каждого молчаливого приклеивания (все три ветки в `_handle_text`: единственная активная заявка, единственная открытая заявка, неоднозначный выбор). Кнопки меню теперь и в подтверждениях «Заявка создана»/«Переключено на» — раньше их не было.

### Кнопка «Закрыть заявку» — цепочка статусов, а не отдельный переход
По прямому запросу заказчика (клиент должен уметь закрыть свою заявку сам, не дожидаясь инженера). `CLOSED` достижим только из `RESOLVED` (`ALLOWED_TRANSITIONS`), поэтому `_close_via_client` не делает отдельный «клиентский» переход в обход правил, а прогоняет заявку по тем же одношаговым переходам, что и `transition_status` уже проверяет: `NEW/ASSIGNED/WAITING_* → IN_PROGRESS → RESOLVED → CLOSED`. Уточняющий вопрос — заказчик выбрал именно это (а не «отменить» или «кнопка только из Решена»), приняв, что клиент увидит уведомление о каждом промежуточном статусе плюс запрос CSAT, а не одно сообщение — так SLA/audit-бухгалтерия остаётся идентичной обычному закрытию инженером, без дублирования логики. Кнопка видна только пока заявка «закрываемая» (`_CLOSEABLE_STATUSES` = открытые статусы + `RESOLVED` — `RESOLVED` намеренно не входит в `OPEN_TICKET_STATUSES`, но закрыть его можно и нужно). Проверено вживую: заявка в статусе «Новая» после одного нажатия кнопки корректно прошла `new → in_progress → resolved → closed`, включая запрос оценки.

## Сквозной аудит проекта (2026-08-01)

Заказчик попросил провести полный аудит и исправить найденное. Ниже — что оказалось сломано и как починено; всё закрыто регресс-тестами (`tests/test_audit_fixes.py`, 20 тестов) и проверено вживую, а не только «по коду».

### Молча не работал сброс исполнителя и команды
Самый заметный пользователю дефект. В карточке заявки выпадающие списки «Не назначено» и «Без команды» отправляли `assigned_engineer_id: null` / `team_id: null`, запрос возвращал 200, интерфейс показывал успех — но `update_ticket` проверял `if payload.assigned_engineer_id is not None`, то есть **любой `null` молча отбрасывался**, и исполнитель оставался прежним. Причина в том, что одна проверка пыталась отвечать на два разных вопроса: «поле не прислали» и «поле прислали пустым» — для необязательных полей это разные вещи. Исправлено через `payload.model_fields_set` (pydantic отдаёт список именно *присланных* полей): `null` теперь очищает поле, отсутствие поля по-прежнему его не трогает. Оба сценария закреплены тестами, включая обратный (PATCH без упоминания исполнителя не должен его снимать) — иначе «исправление» легко переехало бы в противоположный баг. Та же правка применена к `category_id`/`asset_id`.

### Эскалация привилегий: руководитель мог стать администратором
`PATCH /users/{id}` был закрыт только `require_manager_or_above`, а тело запроса позволяет менять `role` и `password` любому пользователю. Следствие: любой руководитель мог одним запросом выдать себе роль администратора либо сменить пароль администратора и захватить его учётную запись. Роль `require_admin` в `deps.py` при этом была объявлена, но нигде не использовалась — заготовка, до которой не дошли руки. Добавлен `_guard_admin_scope`: назначить роль администратора или изменить существующую учётную запись администратора может только администратор; руководитель по-прежнему управляет инженерами и диспетчерами. Отдельно запрещена деактивация собственной учётной записи (защита от самоблокировки). Проверено живыми запросами: 403 на обе попытки эскалации, 400 на самодеактивацию, легитимное создание инженера — 201.

### Сотрудник не мог сменить себе пароль
Пароль задавался только через `PATCH /users/{id}` (руководитель и выше) — то есть инженер не мог сменить даже выданный ему первичный пароль, а сменить его «после первого входа» README требовал. Добавлен `POST /auth/me/password` с проверкой текущего пароля и минимальной длиной нового, плюс раздел «Смена пароля» в профиле. Активные refresh-токены пользователя при смене отзываются — иначе украденная сессия пережила бы пароль, против которого её выдали.

### Вложения: принимались, но были недоступны — мёртвая функция
Файлы из email, MAX и Telegram складывались на диск и записывались в БД, метаданные возвращались в API — но **эндпойнта скачивания не существовало вовсе**, а интерфейс не показывал вложения и не давал их прикрепить (во всём фронтенде слово `attachment` встречалось ровно один раз — в определении типа). То есть весь путь вложений с Этапов 4–5 работал «в один конец». Добавлены: `GET /tickets/{id}/attachments/{attachment_id}` (вложение ищется через сообщение своей заявки, поэтому чужой id даёт 404, а не утечку файла), отображение вложений в переписке, прикрепление файлов к ответу инженера. Скачивание идёт через `fetch` с заголовком авторизации и `Blob`, а не через `<a href>` — обычная ссылка не умеет передать Bearer-токен.

**Пойманный на живой проверке баг в собственной правке:** прикреплённый файл не появлялся в списке. Причина — классическая ловушка React: `setPendingFiles((files) => [...files, ...Array.from(e.target.files)])` вычисляется отложенно, уже **после** соседней строки `e.target.value = ""`, которая очищает `FileList`. Файлы читаются в переменную до сброса инпута. Сброс нужен, чтобы один и тот же файл можно было выбрать повторно. Без прогона в браузере этот дефект прошёл бы: типы сходятся, тесты бэкенда зелёные.

### Небезопасное имя файла
Имя вложения подставлялось в путь хранения как есть, а приходит оно из недоверенных источников (MIME-часть письма, документ из Telegram, загрузка из браузера). Имя вида `../../etc/cron.d/evil` влияло на то, куда попадут байты. Добавлен `safe_filename`: отбрасывает каталог (и POSIX-, и Windows-разделители — почтовые клиенты присылают оба), убирает управляющие символы и ведущие точки, ограничивает длину с сохранением расширения. Проверяется параметризованным тестом, включая проверку того, что файл физически остаётся внутри каталога вложений.

### Бот в групповом чате превращал любое сообщение в заявку
Ни `telegram_channel`, ни `max_channel` не смотрели на тип чата, а у бота включено `can_join_groups`. Достаточно было добавить бота в группу, чтобы каждая реплика в ней создавала заявку от имени случайного контакта. Добавлены `_is_private_chat` / `_is_dialog`: обрабатываются только личные диалоги. Отсутствующее поле типа трактуется как личный чат — молчащий бот хуже, чем одна лишняя заявка, если платформа однажды изменит формат.

### Прочее
- **Дрейф моделей и БД.** Индексы `messages.max_message_id`/`telegram_message_id` создавались миграциями, но не были объявлены в моделях: `compare_metadata` показывал два расхождения, а следующая автогенерация миграции попыталась бы эти индексы удалить. Объявлены в моделях (`index=True`), расхождений — ноль. Проверка `alembic.autogenerate.compare_metadata` оказалась самым результативным инструментом аудита схемы и годится как разовая команда при подготовке релиза.
- **CSAT был не виден в карточке заявки.** Оценка собиралась ботами с Этапа 5 и попадала в отчёты, но `TicketRead` её не отдавал — по конкретной заявке узнать оценку было нельзя. Поля добавлены в схему и выведены в свойствах заявки.
- **Не было интерфейса управления сотрудниками.** API пользователей существовал с Этапа 1, но UI не было ни одного экрана: завести инженера можно было только curl-ом. Добавлен раздел «Настройки → Сотрудники» (создание, смена роли, деактивация) с учётом правил выше: выбор роли администратора недоступен неадминистратору.

### Что осознанно не менялось
- **`cors_origins = ["*"]`** — для локальной разработки; перед публикацией наружу список нужно сузить до фактических доменов панели. Токен хранится в `localStorage` и не отправляется браузером автоматически, поэтому прямой эксплуатации нет, но оставлять `*` в проде не следует.
- **Websocket-уведомления** — по-прежнему REST-опрос, см. раздел про Этап 4 выше.
- **Пагинация списка заявок** — `GET /tickets` возвращает всё без ограничения. На текущих объёмах это не проблема, но при росте базы станет ею; отмечено как известный технический долг, а не исправлено «на всякий случай».

## Пагинация и Этап 6 — телефония Plusofon (2026-08-01)

### Пагинация: заголовок вместо обёртки ответа
`GET /tickets` получил `limit`/`offset`/`q`, а общее число совпадений возвращается заголовком `X-Total-Count`, а не полем в теле. Причина: тело осталось обычным массивом, поэтому ни один существующий потребитель (карточка организации, дашборд, канбан) не сломался от смены контракта — менять пришлось только те места, которым действительно нужна была страница. Максимум `limit` ограничен сервером (200), чтобы параметр из URL не превращался в «выгрузи всё».

**Поиск пришлось перенести на сервер.** Раньше строка поиска фильтровала уже загруженный массив — при постраничной выдаче это искало бы только внутри текущей страницы, то есть тихо врало бы. Отдельный нюанс: люди ищут по номеру `OH-1042`, который они видят, но `display_number` — вычисляемое свойство Python, а не колонка. Поэтому `_search_filter` разбирает запрос обратно в число (`OH-`/`#`/просто цифры) и ищет по `Ticket.number`, иначе поиск по видимому номеру не находил бы ничего.

**Счётчики дашборда переехали в SQL.** Дашборд считал «открытых / нарушений SLA / новых» перебором загруженного списка заявок. С пагинацией это стало бы враньём: цифры показывали бы только первую страницу. Добавлен `GET /tickets/stats` — счётчики считаются в базе по всей очереди. Это как раз тот случай, когда пагинация ломает не сам список, а зависящий от него виджет; такие места надо искать отдельно, компилятор их не покажет.

**Канбан-доска** запрашивает больший лимит (200), поскольку доска по смыслу показывает весь поток работ, а не страницу; если заявок больше, под доской выводится честная строчка «показаны N из M — уточните фильтры», а не молчаливое усечение.

### Пагинация «Мои заявки» в ботах — заодно исправлен скрытый дефект сортировки
Список в MAX и Telegram отдавался как «10 новейших, затем открытые наверх». При разборе выяснилось, что это скрытый дефект: сортировка применялась **после** отсечения окна, поэтому открытая заявка, созданная раньше десяти недавно закрытых, вообще не попадала в список — то есть исчезала ровно та заявка, ради которой клиент чаще всего и открывает список. Теперь сортировка (открытые первыми, внутри группы — новые первыми) выполняется в SQL, и уже к ней применяется страница. Постранично по 5 штук с кнопками «Показать ещё →» / «← Назад»; смещение едет внутри `callback payload` (`mytickets:5`), поэтому не понадобилось хранить позицию листания в состоянии диалога. Логика общая для обоих ботов (`messenger_common.my_tickets_page/buttons/caption`).

### Этап 6: звонок — отдельная сущность, а не поля в заявке
`Call` заведён самостоятельной таблицей: большинство звонков заявкой не становятся (ответили и решили на месте), а у заявки, созданной из звонка, всё равно есть собственные факты звонка — номер, тайминги, длительность, запись, — которым в самой заявке места нет. Связь `Call.ticket_id` необязательная в обе стороны.

**Идемпотентность по `external_id`.** Один звонок приходит несколькими событиями (`ringing` → `answered` → `completed`), и все они несут один и тот же идентификатор звонка провайдера. Приём событий — upsert по нему, а не вставка на каждое событие; поля заполняются только теми значениями, которые в событии реально есть, иначе позднее событие `completed` затирало бы номер, пришедший в `ringing`. Проверено вживую: три события по одному звонку → одна строка и одна заявка.

**Маппинг полей вебхука вынесен в настройки, а не зашит в код.** Имена полей Plusofon (`call_id`, `caller_id`, `status`, …) заданы как значения по умолчанию, но переопределяются в форме настроек канала. Это прямое следствие опыта с MAX (см. выше): формат, переписанный из публичной документации без живого доступа, разошёлся с реальностью в трёх местах сразу и каждое расхождение требовало правки кода и передеплоя. Здесь расхождение чинится редактированием формы. По той же причине словарь статусов провайдера (`no_answer`, `busy`, `cancel`, …) сведён к внутреннему enum через таблицу синонимов, а **неизвестный статус трактуется как «завершён», а не как «пропущен»** — иначе незнакомое значение молча плодило бы фантомные заявки о пропущенных звонках.

**Идентификация по номеру переиспользует нормализацию мессенджеров** (`messenger_common.find_contact_by_phone`, сравнение по последним 10 цифрам) — один и тот же человек опознаётся одинаково, пишет он или звонит, независимо от формата `+7`/`8`/пробелов.

**Пропущенный с неизвестного номера тоже становится заявкой** — контакт создаётся неподтверждённым в организации «Неизвестные», номер сохраняется. Пропущенный звонок с незнакомого номера — ровно тот случай, который диспетчер обязан увидеть, поэтому «не опознали → промолчали» здесь неприемлемо.

**Вебхук защищён общим секретом** (`X-Webhook-Secret`, сравнение через `hmac.compare_digest`) — JWT тут неприменим, у АТС нет пользовательской сессии. На неразобранное событие эндпойнт отвечает `202`, а не `4xx`: провайдер с ретраями иначе будет долбить endpoint из-за события, которое всё равно никогда не разберётся; событие пишется в лог.

**Уведомление диспетчера — опрос, не всплывающее окно.** ТЗ (2.4) просит «всплывающее событие у диспетчера»; websocket-инфраструктуры по-прежнему нет (см. Этап 4), поэтому сделан раздел «Звонки» с опросом раз в 10 секунд и фильтром «только необработанные». Это честная замена, но не буквальное выполнение пункта — полноценный push появится вместе с websocket-уведомлениями.

**Click-to-call не делался** — ТЗ помечает его «желательно, не блокирует релиз», а без доступа к боевому аккаунту Plusofon проверить его всё равно нечем.

**Важно:** вся интеграция написана по документации и проверена только синтетическими событиями (как MAX до боевого токена). Перед вводом в эксплуатацию нужно завести реальный аккаунт Plusofon, направить вебхук на `/webhooks/telephony` и сверить фактические имена полей с формой настроек канала.

## Закрытие долга по ТЗ и Этап 8 — портал клиента (2026-08-01)

По итогам сравнения с конкурентами заказчик попросил взять найденные пробелы в работу. Порядок выбран такой: сначала невыполненные требования собственного ТЗ (дешёвые и с ежедневной пользой), затем портал. Расширения за пределы ТЗ (регулярные заявки, интеграция с мониторингом) сознательно не делались — это изменение объёма, его нужно согласовывать отдельно.

### Поиск: искал по теме, а находить надо было в переписке
Строка поиска покрывала только тему и номер. Для заявок из почты и мессенджеров тема генерируется автоматически (первые 200 символов сообщения или «Обращение из MAX»), поэтому осмысленный текст живёт в переписке — и найти такую заявку по сути было нельзя. Добавлен поиск по телу сообщений через `EXISTS`, а не `JOIN`: при join заявка, совпавшая и по теме, и по трём сообщениям, вернулась бы четырьмя строками. Закреплено тестом.

### Шаблоны ответов
`ResponseTemplate` с необязательной привязкой к категории: шаблон без категории предлагается везде, с категорией — только по заявкам этой категории. Вставка **дописывает** текст к уже набранному, а не заменяет его: инженер обычно сначала пишет пару слов по ситуации, а потом добавляет типовой блок.

### Связанные заявки
`parent_ticket_id` писался с момента появления сценария «поднять старую» в ботах, но нигде не отображался — то есть связь исправно сохранялась и была невидима. Добавлен эндпойнт, возвращающий и родителя, и потомков одним списком, и панель в карточке.

### Экспорт отчётов: XLSX сделан, PDF — нет
ТЗ (р. 9) требует «экспорт XLSX/PDF». Сделан XLSX: именно его руководитель дорабатывает перед отправкой клиенту. PDF **сознательно не делался** — серверный рендеринг потребовал бы тащить в образ браузер или LaTeX ради результата, который не лучше «открыть xlsx и напечатать в PDF». Фиксирую это как осознанно невыполненную половину требования, а не как забытый пункт: если заказчику нужен именно PDF (например, для подписи), решение стоит обсудить отдельно.

### Отчёт клиенту за период (9.2)
Единственный из пяти отчётов ТЗ, которого не было. Состав намеренно узкий — только то, на что клиент имеет право: его заявки, списанное время, расход пакета часов. Ни имён инженеров, ни внутренних заметок, ни сравнения с другими клиентами. **Время суммируется по дате списания, а не по датам заявки** — работа, выполненная в этом месяце по заявке прошлого месяца, попадает в тот месяц, когда её реально потратили, потому что именно так расходуется пакет. Организация без активного договора получает в отчёте «нет договора», а не нули: нули читались бы как «пакет исчерпан».

### Портал клиента (Этап 8, р. 7)

**Отдельная сущность аутентификации, а не роль пользователя.** `PortalCredential` привязан к `Contact`, а не к `User`. Сотрудники и клиенты — разные популяции с разными жизненными циклами, и главное: клиент не должен иметь токен, который примет админский API. Разделение проведено по типу токена — `type: "portal"` против `type: "access"`; `deps.get_current_user` принимает только второй, `portal.get_current_contact` — только первый. Проверено вживую в обе стороны: портальный токен даёт 401 на `/tickets` и `/users`, админский — 401 на `/portal/me`.

**Одна точка решения о видимости.** Все чтения портала идут через `visible_tickets_query`: свои заявки, либо все заявки организации, если у контакта включён `can_view_org_tickets` (р. 6). Это сделано одной функцией специально — портал единственное место, где данных касается посторонний, и правило «что моё» должно быть в одном месте, которое легко проверить, а не выводиться заново в каждом эндпойнте. Отдельно проверено, что даже с флагом организации чужая организация не видна.

**Внутренние заметки не попадают в портал** — `visible_messages` отдаёт только входящие и исходящие. Внутренние заметки это ровно то, что писалось не для клиента (подсказки диспетчеру, пометки о неоднозначной привязке от канальных адаптеров).

**Magic-link.** Токен хранится хешем (как refresh-токены сотрудников) — утёкшая строка в БД не должна быть логином; одноразовый (`used_at`), иначе ссылка в почте остаётся действующим ключом весь свой срок. Ответ на запрос ссылки **одинаков для известного и неизвестного адреса** — иначе эндпойнт превращается в справочник «у кого из сотрудников клиента есть кабинет». По той же причине совпадают тексты ошибок при неверном пароле и несуществующем адресе.

**Заявка с портала всегда от имени вошедшего контакта** — `contact_id` из тела запроса не принимается вообще, клиент не может подать заявку «от коллеги».

**Расход пакета показывается только контактам с `can_view_org_tickets`** — это коммерческая цифра по всей компании, а не персональная.

**Портал ветвится в `main.tsx` по пути, а не маршрутом внутри админского SPA** — у него своя аутентификация, своё хранилище токена (`sd_portal_token`, отдельный ключ, чтобы клиентская и сотрудничья сессии могли сосуществовать в одном браузере) и никакого админского обвеса. Ветвление на корне гарантирует, что ничто под `/portal` не может провалиться на сотруднический экран. В проде портал ставится на поддомен (как требует ТЗ) — nginx направляет поддомен на `/portal`, бандл один и тот же.

**Мобильная вёрстка** проверена прогоном в эмуляции iPhone: вход, создание обращения, переписка, отсутствие горизонтального скролла. Размер шрифта полей ввода — 16px намеренно: меньший размер заставляет Safari на iOS зумить страницу при фокусе.

## Сохраняемые фильтры, PDF, плановые заявки и мониторинг (2026-08-01)

### PDF: моя первоначальная оценка была неверной
Раньше я записал, что PDF потребует «браузер или LaTeX», и отказался. Это верно только для пути HTML→PDF (weasyprint, wkhtmltopdf). `reportlab` рисует документ напрямую — одна библиотека, без системных зависимостей, кроме шрифта. Отказ был поспешным, и заказчик правильно попросил доделать.

Единственное системное требование — TTF с кириллицей: встроенные в reportlab шрифты Type1 кириллицы не содержат, и без внешнего шрифта весь русский текст вышел бы чёрными квадратами. В образ ставится `fonts-dejavu-core` (~1 МБ). `report_pdf._ensure_fonts` регистрирует шрифт один раз на процесс и **возвращает False, а не падает**, если шрифта нет — эндпойнт тогда отдаёт 503 с внятным текстом вместо PDF с квадратами: испорченный документ, ушедший клиенту, хуже явной ошибки. Проверено рендерингом в изображение и просмотром глазами (побайтовая проверка наличия шрифта этого не доказывает).

PDF сделан **только для отчёта клиенту**. Именно он уходит наружу, где важна фиксированная вёрстка; внутренний сводный отчёт остаётся XLSX, потому что его дорабатывают, а не печатают.

### Сохраняемые фильтры (8.1)
Персональные, а не общие: «мои просроченные» у каждого инженера свои, а общий список быстро зарастёт чужими выборками. Критерии хранятся JSON-ом, потому что они буквально повторяют query-параметры `GET /tickets` — вынос в колонки означал бы миграцию на каждый новый фильтр очереди. Сохранение под существующим именем перезаписывает фильтр: это и есть смысл слова «сохранить», а 409 просто заставил бы удалять и повторять.

### Плановые (регулярные) заявки — вне исходного ТЗ, по согласованию
В ТЗ этого нет, но для MSP на абонентском обслуживании профилактика по расписанию — базовая вещь (у Okdesk есть), иначе она живёт в чьём-то календаре и забывается. Расписание порождает **обычную заявку** через `tickets_service.create_ticket`, поэтому SLA, маршрутизация, биллинг и отчёты работают без единой правки — это источник заявок, а не второй сорт заявок.

Периодичность — короткий фиксированный список (день/неделя/месяц/квартал), а не cron-выражение: у сервисной компании работы недельные и месячные, а cron в админской форме это нагрузка на поддержку без пользы.

**Арифметика дат — то место, где легко ошибиться.** `_add_months` зажимает день по длине месяца, поэтому расписание «31-го числа» в феврале срабатывает 28-го **и не остаётся навсегда на 28-м** — следующий месяц снова 31-е. Недельное расписание в свой же день недели прыгает на неделю вперёд, а не возвращает сегодня (иначе следующий проход воркера запустил бы его повторно). Просроченное расписание (воркер лежал неделю) срабатывает **один раз** и переносится от сегодня, а не добивает все пропущенные периоды: пачка протухших заявок о профилактике никому не поможет. Если создание заявки упало, расписание всё равно двигается вперёд — иначе сломанное расписание (удалённый контакт) ретраится каждый проход вечно.

### Интеграция с мониторингом — вне исходного ТЗ, по согласованию
MSP узнаёт о большинстве инцидентов от мониторинга, а не от клиента. Вебхук намеренно повторяет телефонный: общий секрет, настраиваемый маппинг полей, идемпотентность по идентификатору события источника.

- **Флаппинг не плодит заявки** — повторный PROBLEM по тому же `external_id` обновляет существующий алерт. Одна авария — одна заявка.
- **Неизвестный статус трактуется как проблема, а не как recovery.** Пропущенное восстановление оставит заявку открытой, и её закроет человек; ошибочное восстановление молча закроет живой инцидент. Асимметрия ущерба очевидна.
- **Recovery переводит в «Решена», а не в «Закрыта»** — тем же одношаговым путём, что и клиентское закрытие. Пропал симптом, но никто это не проверил; дальше работает обычное правило автозакрытия (4.2).
- **Severity → приоритет** по таблице (disaster/critical → P1, high → P2 и т.д.), чтобы авария не легла в очередь как рядовая заявка.
- **Алерт с неизвестной организацией всё равно становится заявкой** — уходит в «Неизвестные» на синтетический контакт «Система мониторинга». Потерять алерт из-за того, что некому его приписать, недопустимо.
- Настройки живут в конфиге канала `PORTAL` под ключом `monitoring`: мониторинг не клиентский канал, заводить ради него член перечисления означало бы миграцию и фантомную карточку в интерфейсе каналов.

Ни то, ни другое **не проверено на боевых системах** — только синтетическими событиями. Перед вводом нужно направить вебхук из реального Zabbix и сверить имена полей с формой настроек.

## Этап 10: эксплуатация, уведомления в реальном времени, нагрузочная проверка (2026-08-03)

### Живые уведомления через Postgres LISTEN/NOTIFY, а не Redis
Уведомления должны приходить мгновенно, а не через 30 секунд опроса. Очевидный ход — Redis pub/sub, но это **ещё один контейнер, который заказчику придётся администрировать**, ради одной функции. Postgres уже стоит, уже обязателен и умеет `LISTEN`/`NOTIFY` — этого достаточно для фан-аута между `app` и `worker`.

`publish_notification` выполняет `SELECT pg_notify(...)` **внутри той же транзакции**, что и создание уведомления: уведомление о ещё не закоммиченном событии — это гонка, при которой клиент дёргается за данными, которых пока нет.

Опрос **оставлен как запасной путь**, а не выключен. Websocket рвётся о прокси, VPN и спящий ноутбук; поведение «уведомления не пришли вообще» гораздо хуже, чем «пришли через полминуты».

Токен передаётся query-параметром — браузерный WebSocket не умеет ставить заголовки. Соединение с чужим типом токена (портальным) **сначала принимается и только потом закрывается** кодом 1008: закрытие до `accept()` рвёт handshake на уровне HTTP, и клиент видит бессмысленный 1006 вместо «токен не тот». Фронтенд на 1008 переподключается редко, а не сдаётся — за этим кодом чаще всего просто истёкший токен.

nginx без `proxy_http_version 1.1` и заголовков `Upgrade`/`Connection` рубит апгрейд молча: напрямую к контейнеру всё работало, через прокси — нет.

### Таймер работы над заявкой
Таймер принадлежит **сотруднику, а не заявке**: инженер не работает над двумя заявками одновременно. Запуск таймера по второй заявке останавливает первый и **списывает накопленное время, а не выбрасывает его** — работа была, и потерять её молча хуже, чем оставить запись, которую можно поправить.

Порог мис-клика проверяется **в секундах, до округления**. Первая версия сравнивала уже округлённые минуты с единицей и не срабатывала никогда: `ceil()` превращает в минуту даже полсекунды. Ошибка в одну строку, которую не видно при чтении, — поймана тестом на пятисекундный таймер.

Время округляется вверх: недосписать клиенту хуже, чем списать лишнюю минуту.

### Отчёты на годовом объёме: 2850 мс → приемлемо
Нагрузочная проверка (ТЗ р. 11) на 500 заявок в день за год — 182 500 заявок. Очередь, поиск и карточка держались отлично (52 / 2 / 1 мс), а **сводный отчёт за месяц занимал 2,85 секунды**. На тридцатидневной базе он же занимал 574 мс, то есть на реальных объёмах проблема выросла бы линейно и вылезла бы уже у заказчика.

Причин было две, и обе типичные:

1. **Агрегация в Python вместо SQL.** Секции отчёта выгружали все заявки периода ORM-объектами и считали по ним циклами. 15 000 объектов — около 300 мс на одну выгрузку, а секций несколько. Хуже всех была «старение бэклога»: у неё нет периода по смыслу, поэтому она поднимала **весь незакрытый бэклог за всё время**. Переписано на `COUNT`/`AVG`/`CASE` в базе.
2. **Индексов на `tickets` не было вообще** — только первичный ключ и уникальность номера. Любой фильтр по дате, статусу или организации разворачивался в полный просмотр таблицы (миграция `c3e91a5d70f4`). Индексы заведены по фактическим запросам, а не «на всякий случай»: каждый замедляет вставку, а заявки создаются постоянно.

Отдельно отмечу: **это нашлось только нагрузочной проверкой**. Функционально отчёт был правилен всё время, тесты проходили, на глаз в интерфейсе всё летало.

### Резервное копирование
В копию входит `.env` — не из-за паролей, а из-за `SETTINGS_ENCRYPTION_KEY`: без него восстановленная база отдаст токены ботов и пароли почты нерасшифруемым мусором, и все каналы придётся настраивать заново. Это самая неочевидная часть восстановления, поэтому о ней написано и в скрипте, и в `docs/deployment.md`.

`restore.sh` перед разворачиванием снимает **страховочный дамп текущего состояния** и требует ввести «да»: восстановление не из той копии — типичная авария, и откатить её должно быть возможно. Проверено полным циклом: заявка, созданная после копии, после восстановления исчезает.

### Небезопасные значения по умолчанию: предупреждать, а не отказываться стартовать
`.env.example` лежит в репозитории с рабочим ключом шифрования и `JWT_SECRET=change-me`. При `ENVIRONMENT=production` приложение громко пишет в лог, что именно осталось дефолтным, но **не отказывается запускаться**: отказ оставил бы админа посреди развёртывания с системой, которая не поднимается, и он бы просто откатил версию. Внятное предупреждение в логах — то, по чему реально что-то делают.

### pytest в образ не входит; локальный цикл — через `docker-compose.override.yml`
Тестовые зависимости ставились руками в запущенный контейнер и **молча исчезали при каждой пересборке**; заодно исходники вшиты в образ, поэтому новый файл с тестами внутри контейнера не появлялся. Приведено к стандартной схеме Compose: боевой `docker-compose.yml` без изменений, а локальный `docker-compose.override.yml` (в `.gitignore`) монтирует исходники и собирает образ с `INSTALL_DEV=true`. На машине заказчика оверрайда нет — значит, нет ни pytest, ни бинд-маунтов.

## Проверка интеграции с Zabbix живьём (2026-08-03)

Интеграция была написана и покрыта тестами, но никто ни разу не проходил
её путь целиком — от «включить» до «пришло событие». Первая же попытка
настроить её как настроил бы администратор вскрыла три вещи.

**`hmac.compare_digest` падает на не-ASCII.** Секрет вебхука вводит человек,
и кириллица в нём совершенно реальна — а `compare_digest` на таких строках
возбуждает `TypeError`, и вебхук отдавал **500 вместо 401**. Задето было оба
вебхука, телефонии и мониторинга, потому что код был скопирован. Проверка
секрета вынесена в `deps.verify_webhook_secret` — теперь она одна на оба.

Дальше выяснилось, что кириллический секрет не спасти простым `.encode()`:
HTTP-заголовки декодируются как latin-1, поэтому такой секрет совпал бы в
query-параметре и не совпал бы в заголовке — интеграция работала бы через
раз в зависимости от того, как её настроили. Поэтому не-ASCII секрет вебхука
**запрещён при сохранении**, с объяснением причины в тексте ошибки. Лучше не
дать завести полурабочую настройку, чем разбираться потом, почему «иногда
не приходит».

**`GET /monitoring/alerts` всегда отдавал 500.** В схеме ответа `created_at`
и `resolved_at` были объявлены `str` вместо `datetime`, и любой непустой
список валился на сериализации. Тесты этого не видели, потому что дёргали
сервисный слой напрямую, минуя эндпоинт. Добавлен тест именно на эндпоинт.

**Формы настроек в интерфейсе нет.** Настройки мониторинга живут в конфиге
канала «Портал», а `CONFIGURABLE_CHANNELS` портал не включает — то есть
включить интеграцию можно только запросом к API. В `docs/deployment.md` я
при этом написал, что мониторинг настраивается в Настройки → Каналы. Это
была неправда; документация исправлена, порядок настройки описан в
`docs/monitoring.md`. Форму стоит сделать отдельно.

Общий вывод тот же, что и с ботами MAX и Telegram: **пока интеграцию не
прошли руками от начала до конца, она не проверена**, сколько бы тестов на
неё ни было. Тесты здесь покрывали бизнес-логику алертов и были правы —
ошибки сидели ровно на стыках, которых тесты не касались: разбор заголовка,
сериализация ответа, доступность настройки.

### Форма настроек мониторинга: отдельный ресурс, а не карточка канала

Настройки мониторинга физически лежат в конфиге канала «Портал», но в
интерфейс это протекать не должно. Добавить `PORTAL` в `CONFIGURABLE_CHANNELS`
было бы на одну строку дешевле и дало бы в списке каналов карточку «Портал» —
запись, которую нельзя ни настроить, ни выключить осмысленно. Поэтому
заведён отдельный ресурс `/settings/monitoring` со своими схемами: наружу он
описывает мониторинг, а где это хранится — деталь реализации.

`field_map` **отдаётся полным, а сохраняется только отличиями от умолчаний.**
Форме нужны все поля, иначе администратор решит, что маппинг надо заполнять
с нуля; но если писать в конфиг полную карту, то изменение умолчаний в коде
никогда не дойдёт до уже настроенных установок — они навсегда останутся со
старыми именами полей.

Секрет вебхука следует общему правилу форм каналов: пустое поле означает «не
менять», отдельная кнопка — «снять». Различие «ключ не передан» и «передан
null» берётся из `model_fields_set` — без него снять секрет было бы
невозможно, а сохранение формы стирало бы уже заданный.

**Побочно найдена коллизия в CSS.** `.form-row` задаёт
`flex-direction: column`, а `.form-row-inline` его не сбрасывал: там, где оба
класса стоят вместе (чекбоксы в формах каналов), подпись уезжала под
чекбокс и вставала по центру строки. Существовало это и в карточке телефонии,
просто никто не смотрел. Направление прописано явно.

## Ежемесячные отчёты клиентам (2026-08-03)

### Отчёт хранится снимком, а не пересчитывается на лету
Ключевое решение. Отчёт клиенту — документ, который уходит наружу: если
считать его по запросу, то списание, внесённое задним числом, или
переоткрытая заявка **молча изменят цифры за прошлый месяц**, уже
отправленные клиенту. Расхождение всплывёт при сверке счёта, и объяснять
его придётся не системе.

Поэтому `ClientReport` хранит полный ответ `get_client_report` в JSONB на
момент формирования. Чтобы получить свежие цифры, отчёт надо сформировать
заново — явным действием, и повторное формирование **снимает отметку
«отправлен»**: у клиента на руках старая версия, и говорить про новый снимок
«отправлен» было бы неправдой.

Название организации тоже берётся из снимка: клиента могли переименовать
после отправки, а в списке должно стоять то имя, под которым документ ушёл.

### Автоформирование без отправки
Заказчик выбрал «формировать самим, отправлять руками». Проход идёт на том
же тике воркера, что и расписания, но привязки к «ровно 1-го числа в 00:00»
нет: отчёты формируются при первом запуске после начала месяца, поэтому
ночной простой воркера ничего не ломает. Идемпотентность по ключу
(организация, начало, конец), и **автопроход не перезаписывает уже
существующий отчёт** — руководитель мог переформировать его вручную после
исправления списаний, и затирать эту работу нельзя.

Падение на одной организации не должно оставить без отчётов остальных —
цикл ловит исключение по каждому клиенту отдельно, с откатом транзакции.

Отчёты формируются по организациям, у которых есть договор: без договора нет
ни пакета часов, ни обязательств по SLA, и ежемесячный отчёт такому клиенту
не отправляют.

### Состав отчёта
Добавлены соблюдение SLA и разбивки по каналам и категориям (выбор
заказчика). Нарушения SLA показываются **числом, а не списком**: перечень
собственных промахов в документе, который вы сами отправляете клиенту,
читается как претензия к себе. Имён инженеров в отчёте нет — это правило
из Этапа 8 сохраняется, и на него есть тест.

### PDF: документ, а не выгрузка
Прежний PDF был функционален и выглядел служебно: в шапке стояло
`период 2026-07-01 — 2026-07-31`, дальше две таблицы. Переделан: заголовок
периода по-русски («Июль 2026»), полоса крупных показателей сверху, затем
SLA и пакет часов в две колонки, разбивки, и только в конце список
обращений. Клиент читает первые две трети страницы — всё существенное
должно быть там.

**Про вложенные таблицы reportlab.** Двухколоночная вёрстка сначала
переполнялась: текст правой колонки наезжал на левую. Причина в том, что
вложенная таблица строилась шириной с колонку внешней, а отступ ячейки
выталкивал её за край. Ширины считаются так, чтобы содержимое ячейки ровно
совпадало с шириной вложенной таблицы.

### Реестр моделей: autogenerate предлагал снести восемь таблиц
Обнаружено при добавлении `ClientReport`. `app/models/__init__.py` перестали
пополнять после Этапа 5, а `alembic/env.py` берёт `Base.metadata` именно
оттуда — то есть `call`, `response_template`, `portal_auth`, `saved_filter`,
`ticket_schedule`, `monitoring_alert`, `active_timer` для автогенерации
просто не существовали, и первый же `alembic revision --autogenerate`
выдал миграцию с `drop_table` по каждой из них.

Схему это не сломало только потому, что все миграции до сих пор писались
руками. Реестр пополнен, и добавлен тест `test_all_models_are_registered`,
который обходит каталог моделей и падает, если модуль не зарегистрирован, —
уследить за этим глазами нельзя. Рядом — тест на отсутствие дрейфа схемы
относительно моделей.

### Отчёт клиенту остался в одном месте
Он существовал дважды: панель на странице «Отчёты» считала его на лету, а
раздел «Отчёты клиентам» сохраняет снимком. Два пути к одному документу —
это две версии цифр за один и тот же месяц, причём несохранённая версия
ничем не отличима от той, что ушла клиенту. Панель и эндпоинты
`/reports/client*` удалены; дорога одна — сформировать отчёт (он же снимок)
и скачать его из раздела «Отчёты клиентам».

Заодно в меню «Отчёты» и «Отчёты клиентам» перестали быть двумя соседними
пунктами верхнего уровня и собраны в группу «Отчёты» → «Сводный отчёт» /
«Отчёты клиентам», как справочники и настройки.

### «Отправлен» — отметка, а не действие
Кнопка называлась «Отправлен», хотя система ничего не отправляет: это
пометка для себя, кому отчёт уже ушёл. На кнопке такое слово читается как
команда, поэтому теперь «Отметить отправленным». И отметку **можно снять**:
раньше единственным способом откатить случайное нажатие было
переформирование отчёта — несоразмерно для пометки, которая ничего не
делает.
